## 1. 概述

QEMU 是一个复杂的多线程应用程序，其线程模型包含以下核心组件：

| 组件 | 作用 | 主要文件 |
|------|------|---------|
| **BQL** | 全局互斥锁，保护共享状态 | `cpus.c` |
| **主事件循环** | GLib + AioContext 事件驱动 | `main-loop.c` |
| **vCPU 线程** | 每 vCPU 一个线程（TCG/KVM） | `tcg-accel-ops-mttcg.c`, `kvm-accel-ops.c` |
| **IOThread** | 独立的 I/O 事件循环线程 | `iothread.c` |
| **RCU** | 读侧无锁的共享数据保护 | `util/rcu.c` |
| **协程** | 用户态协作式调度，用于块层 | `util/qemu-coroutine.c` |
| **AioContext** | 异步 I/O 事件上下文 | `util/async.c`, `util/aio-posix.c` |

这些组件协同工作，实现了 QEMU 的高效并发模型：vCPU 线程执行客户机代码时释放 BQL；块层通过协程实现异步 I/O；RCU 保护频繁读取的共享数据（如 FlatView）免受锁竞争。

## 3. BQL（Big QEMU Lock）

### 3.1 定义与初始化

BQL 是一个普通的 `QemuMutex`（**非递归**），定义在 `cpus.c:69-70`：

```c
/* The Big QEMU Lock (BQL) */
static QemuMutex bql;
```

初始化在 `qemu_init_cpu_loop()` 中（`cpus.c:427-435`）：

```c
void qemu_init_cpu_loop(void)
{
    qemu_init_sigbus();
    qemu_cond_init(&qemu_cpu_cond);
    qemu_cond_init(&qemu_pause_cond);
    qemu_mutex_init(&bql);
    qemu_thread_get_self(&io_thread);  // 主线程 = IO 线程
}
```

### 3.2 API

BQL 的核心 API 定义在 `main-loop.h:259-384`：

| 函数 | 作用 |
|------|------|
| `bql_lock()` | 获取 BQL |
| `bql_unlock()` | 释放 BQL |
| `bql_locked()` | 检查当前线程是否持有 BQL |
| `qemu_in_main_thread()` | 等价于 `bql_locked()` |

实现（`cpus.c:573-586`）：

```c
void bql_lock_impl(const char *file, int line)
{
    QemuMutexLockFunc bql_lock_fn = qatomic_read(&bql_mutex_lock_func);
    g_assert(!bql_locked());   // 非递归！不能重复加锁
    bql_lock_fn(&bql, file, line);
}

void bql_unlock(void)
{
    g_assert(bql_locked());
    g_assert(!bql_unlock_blocked);  // 防止在关键区间释放
    qemu_mutex_unlock(&bql);
}
```

### 3.3 BQL 保护的范围

BQL 保护所有 "主循环可见" 的全局状态（`main-loop.h:356-383` 注释）：

- 设备模型状态（MMIO 回调、中断控制器）
- QOM 对象树
- 块设备状态修改
- 定时器注册/注销
- 监控器（Monitor/QMP）命令处理
- vCPU 状态修改（暂停/恢复/热插拔）

### 3.4 BQL 的线程安全状态追踪

BQL 的持有状态通过 TLS 变量追踪（`cpus.c:525-561`）：

```c
QEMU_DEFINE_STATIC_CO_TLS(bool, bql_locked)

bool bql_locked(void) { return get_bql_locked(); }
bool qemu_in_main_thread(void) { return bql_locked(); }
```

`QEMU_DEFINE_STATIC_CO_TLS` 是协程感知的 TLS：在协程环境中，每个协程有独立的 `bql_locked` 副本。

## 4. 主事件循环

### 4.1 初始化

`qemu_init_main_loop()` 创建主 AioContext 并集成 GLib（`main-loop.c:160-187`）：

```c
int qemu_init_main_loop(Error **errp)
{
    qemu_init_clocks(qemu_timer_notify_cb);
    qemu_signal_init(errp);

    qemu_aio_context = aio_context_new(errp);     // 创建主 AioContext
    qemu_set_current_aio_context(qemu_aio_context);
    qemu_notify_bh = qemu_bh_new(notify_event_cb, NULL);

    // 将 AioContext 作为 GSource 附加到 GLib 默认 MainContext
    src = aio_get_g_source(qemu_aio_context);
    g_source_attach(src, NULL);

    // IOHandler 也作为独立 GSource
    src = iohandler_get_g_source();
    g_source_attach(src, NULL);
    return 0;
}
```

### 4.2 主循环执行

`main_loop_wait()` 是主循环的单次迭代（`main-loop.c:563-604`）：

```c
void main_loop_wait(int nonblocking)
{
    // 1. 通知监听器准备 poll
    notifier_list_notify(&main_loop_poll_notifiers, &mlpoll);

    // 2. 计算最短超时（定时器 deadline）
    timeout_ns = qemu_soonest_timeout(timeout_ns,
                                       timerlistgroup_deadline_ns(&main_loop_tlg));

    // 3. 执行平台相关的 poll（释放 BQL！）
    ret = os_host_main_loop_wait(timeout_ns);

    // 4. 运行所有到期定时器
    qemu_clock_run_all_timers();
}
```

### 4.3 BQL 在 poll 期间释放

`os_host_main_loop_wait()` 的核心模式（`main-loop.c:462-547`）：

```c
static int os_host_main_loop_wait(int64_t timeout)
{
    g_main_context_acquire(context);
    g_main_context_prepare(context, &max_priority);
    g_main_context_query(context, ...);

    bql_unlock();                    // ← 释放 BQL
    replay_mutex_unlock();
    g_poll_ret = qemu_poll_ns(...);  // ← 阻塞等待事件
    replay_mutex_lock();
    bql_lock();                      // ← 重新获取 BQL

    g_main_context_check(context, ...);
    g_main_context_dispatch(context);  // 分发 GLib 事件回调
    return ret;
}
```

**关键设计：** 主线程在 `poll()` 期间释放 BQL，允许 vCPU 线程在此期间获取 BQL 来执行 MMIO 等操作。

## 5. vCPU 线程模型

### 5.1 线程创建

每个 vCPU 都有独立的线程。线程函数根据加速器类型不同：

| 加速器 | 线程函数 | 文件 |
|--------|---------|------|
| MTTCG | `mttcg_cpu_thread_fn()` | `tcg-accel-ops-mttcg.c:65` |
| 单线程 TCG | RR 模式线程函数 | `tcg-accel-ops-rr.c:180` |
| KVM | `kvm_vcpu_thread_fn()` | `kvm-accel-ops.c:31` |

线程名格式为 `"CPU %d/TCG"` 或 `"CPU %d/KVM"`。

### 5.2 BQL 与 vCPU 执行的交互模式

vCPU 线程的核心模式是：**持有 BQL 处理事件，释放 BQL 执行客户机代码**。

```
vCPU 线程生命周期:

  bql_lock()
    │
    ├── 循环开始 ──┐
    │              │
    │  qemu_process_cpu_events()    ← 持有 BQL，处理暂停/恢复等
    │              │
    │  if (cpu_can_run) {
    │      bql_unlock()             ← 释放 BQL
    │      tcg_cpu_exec(cpu)        ← 执行客户机代码（不持有 BQL）
    │      bql_lock()               ← 重新获取 BQL
    │  }
    │              │
    │  处理退出原因 ──┘
    │
  bql_unlock()
```

## 6. MTTCG 多线程 TCG

### 6.1 线程函数

MTTCG 模式下，每个 vCPU 线程独立执行（`tcg-accel-ops-mttcg.c:65-122`）：

```c
static void *mttcg_cpu_thread_fn(void *arg)
{
    CPUState *cpu = arg;

    rcu_register_thread();        // 注册 RCU
    tcg_register_thread();        // 注册 TCG TLS
    bql_lock();
    current_cpu = cpu;
    cpu_thread_signal_created(cpu);

    do {
        qemu_process_cpu_events(cpu);  // 处理 vCPU 事件（需要 BQL）

        if (cpu_can_run(cpu)) {
            bql_unlock();              // 释放 BQL
            r = tcg_cpu_exec(cpu);     // 执行客户机代码
            bql_lock();                // 重新获取 BQL

            switch (r) {
            case EXCP_DEBUG:   cpu_handle_guest_debug(cpu); break;
            case EXCP_HALTED:  break;
            case EXCP_ATOMIC:
                bql_unlock();
                cpu_exec_step_atomic(cpu);  // 原子指令需要独占执行
                bql_lock();
                break;
            }
        }
    } while (!cpu->unplug || cpu_can_run(cpu));

    bql_unlock();
    rcu_unregister_thread();
    return NULL;
}
```

### 6.2 EXCP_ATOMIC 处理

当 TCG 遇到需要原子保证的指令（如 LDXR/STXR），会通过 `EXCP_ATOMIC` 退出，由 `cpu_exec_step_atomic()` 以串行方式执行该指令，确保多 vCPU 环境下的内存一致性。

### 6.3 线程启动

`mttcg_start_vcpu_thread()` 创建线程（`tcg-accel-ops-mttcg.c:124-137`）：

```c
void mttcg_start_vcpu_thread(CPUState *cpu)
{
    snprintf(thread_name, ..., "CPU %d/TCG", cpu->cpu_index);
    qemu_thread_create(cpu->thread, thread_name, mttcg_cpu_thread_fn,
                       cpu, QEMU_THREAD_JOINABLE);
}
```

## 7. KVM vCPU 线程

### 7.1 线程函数

KVM vCPU 线程结构类似但更简洁（`kvm-accel-ops.c:31-66`）：

```c
static void *kvm_vcpu_thread_fn(void *arg)
{
    CPUState *cpu = arg;

    rcu_register_thread();
    bql_lock();
    kvm_init_vcpu(cpu, &error_fatal);  // 初始化 KVM vCPU
    kvm_init_cpu_signals(cpu);
    cpu_thread_signal_created(cpu);

    do {
        qemu_process_cpu_events(cpu);
        if (cpu_can_run(cpu)) {
            r = kvm_cpu_exec(cpu);     // 进入 KVM 执行
            if (r == EXCP_DEBUG)
                cpu_handle_guest_debug(cpu);
        }
    } while (!cpu->unplug || cpu_can_run(cpu));

    kvm_destroy_vcpu(cpu);
    bql_unlock();
    rcu_unregister_thread();
    return NULL;
}
```

### 7.2 KVM_RUN 与 BQL

`kvm_cpu_exec()` 在调用 `ioctl(KVM_RUN)` 前释放 BQL（`kvm-all.c:3449-3622`）：

```
kvm_cpu_exec():
    bql_unlock()             ← 释放 BQL（允许其他线程工作）
    cpu_exec_start(cpu)      ← 标记 CPU 开始执行
    ioctl(KVM_RUN)           ← 进入内核态执行客户机代码
    cpu_exec_end(cpu)        ← 标记 CPU 结束执行
    bql_lock()               ← 重新获取 BQL
    处理 VM Exit 原因        ← 持有 BQL 处理 MMIO/IO 等
```

## 8. IOThread

### 8.1 概念

IOThread 是独立于主线程的 I/O 事件循环线程，拥有自己的 AioContext。块设备可以关联到 IOThread 来并行处理 I/O，避免与主线程的 BQL 竞争。

### 8.2 实现

IOThread 运行函数（`iothread.c:28-66`）：

```c
static void *iothread_run(void *opaque)
{
    IOThread *iothread = opaque;

    rcu_register_thread();
    g_main_context_push_thread_default(iothread->worker_context);
    qemu_set_current_aio_context(iothread->ctx);

    while (iothread->running) {
        // 纯块层 IOThread 使用 aio_poll（更高效）
        aio_poll(iothread->ctx, true);

        // 需要 GLib 支持时运行 GMainLoop
        if (iothread->running && qatomic_read(&iothread->run_gcontext)) {
            g_main_loop_run(iothread->main_loop);
        }
    }

    rcu_unregister_thread();
    return NULL;
}
```

### 8.3 IOThread vs 主线程

| 特性 | 主线程 | IOThread |
|------|--------|----------|
| AioContext | `qemu_aio_context`（全局） | 独立 AioContext |
| GLib 集成 | 始终使用 | 可选 |
| BQL | 持有（除 poll 期间） | 不持有 |
| 用途 | 设备模型、监控器、UI | 块设备 I/O |

## 9. AioContext 异步 I/O 上下文

### 9.1 定义

`AioContext` 是 QEMU 的核心事件循环抽象（`include/qemu/aio.h:201-260`），封装了：
- **fd 事件处理器**：文件描述符的读/写/异常事件
- **BH（Bottom Half）**：延迟执行的回调
- **定时器**：多时钟源的定时回调
- **协程调度**：协程的唤醒和恢复

### 9.2 创建

```c
// 主 AioContext（main-loop.c:172）
qemu_aio_context = aio_context_new(errp);

// IOThread 的 AioContext（iothread.c:182-194）

```

### 9.3 aio_poll() 事件循环

`aio_poll()` 是 AioContext 的核心驱动函数（`aio-posix.c:652-758`）：

```
aio_poll(ctx, blocking):
    1. 运行所有待执行的 BH
    2. 检查 fd 事件（通过 epoll/ppoll/io_uring）
    3. 调度就绪的 fd 回调
    4. 检查并执行到期定时器
    5. 恢复被调度的协程
```

## 10. RCU（Read-Copy-Update）

### 10.1 实现

QEMU 实现了自己的用户态 RCU（移植自 liburcu），使用显式内存屏障（`util/rcu.c:1-10` 注释 "urcu-mb.c"）。

核心机制：
- **全局 grace period 计数器** `rcu_gp_ctr`（`rcu.c:49`）
- **每线程读者状态** 通过 TLS 追踪
- **写者（`synchronize_rcu()`）** 递增 `rcu_gp_ctr`，等待所有读者通过静默点

### 10.2 核心 API

| 函数 | 作用 | 文件 |
|------|------|------|
| `rcu_read_lock()` | 进入 RCU 读临界区 | `rcu.h:78-119` |
| `rcu_read_unlock()` | 离开 RCU 读临界区 | `rcu.h:78-119` |
| `synchronize_rcu()` | 等待所有读者完成 | `rcu.c:174-204` |
| `call_rcu1()` | 延迟回调（grace period 后执行） | `rcu.c:331-337` |
| `rcu_register_thread()` | 注册线程为 RCU 读者 | `rcu.c:396-409` |
| `RCU_READ_LOCK_GUARD()` | RAII 风格读锁 | `rcu.h:166-190` |

### 10.3 synchronize_rcu() 实现

```c
void synchronize_rcu(void)
{
    QEMU_LOCK_GUARD(&rcu_sync_lock);
    smp_mb_global();                    // 全局内存屏障

    QEMU_LOCK_GUARD(&rcu_registry_lock);
    if (!QLIST_EMPTY(&registry)) {
        // 递增 grace period 计数器
        qatomic_set(&rcu_gp_ctr, rcu_gp_ctr + RCU_GP_CTR);
        // 等待所有已注册的读者通过静默点
        wait_for_readers();
    }
}
```

### 10.4 call_rcu 线程

QEMU 有专门的 `call_rcu` 线程来执行延迟回收（`rcu.c:281-329`）：

```c
static void *call_rcu_thread(void *opaque)
{
    rcu_register_thread();
    for (;;) {
        // 等待有回调入队
        n = qatomic_read(&rcu_call_count);
        if (!n) qemu_event_wait(&rcu_call_ready_event);

        // 执行 synchronize_rcu() 等待 grace period
        synchronize_rcu();

        // 在 BQL 下执行回调
        bql_lock();
        while (n > 0) {
            node = try_dequeue();
            node->func(node);  // 执行回收回调（如释放 FlatView）
            n--;
        }
        bql_unlock();
    }
}
```

### 10.5 原子 RCU 访问

```c
// 读侧（无锁）
ptr = qatomic_rcu_read(&shared_ptr);    // acquire 语义

// 写侧（更新后发布新指针）
qatomic_rcu_set(&shared_ptr, new_ptr);  // release 语义
// 旧对象通过 call_rcu() 延迟释放
```

## 11. RCU 保护的关键数据结构

### 11.1 FlatView（内存拓扑）

FlatView 是内存子系统最核心的 RCU 保护数据结构：

```c
// 读取当前 FlatView（memory.c:823-834）
FlatView *address_space_get_flatview(AddressSpace *as)
{
    RCU_READ_LOCK_GUARD();
    fv = address_space_to_flatview(as);  // qatomic_rcu_read(&as->current_map)
    flatview_ref(fv);
    return fv;
}

// 更新 FlatView（memory.c 中）
qatomic_rcu_set(&as->current_map, new_view);
call_rcu(old_view, flatview_destroy, rcu);  // 旧 view 延迟释放
```

### 11.2 RAMBlock 列表

`ram_list.blocks` 是 RCU 保护的链表（`ramlist.h:12-59`）：

```c
typedef struct RAMList {
    /* RCU-enabled, writes protected by the BQL. */
    QLIST_HEAD(, RAMBlock) blocks;
    DirtyMemoryBlocks *dirty_memory[DIRTY_MEMORY_NUM];
    ...
} RAMList;
```

## 12. 协程（Coroutine）核心机制

### 12.1 设计目标

QEMU 协程是用户态协作式调度的轻量级执行单元，主要用于块层 I/O 操作。协程允许代码以同步风格编写异步逻辑，避免回调地狱。

### 12.2 Coroutine 结构

```c
// coroutine_int.h:44-70
struct Coroutine {
    CoroutineEntry *entry;       // 入口函数
    void *entry_arg;             // 入口参数
    Coroutine *caller;           // 调用者（用于 yield 返回）
    size_t locks_held;           // 持有的锁计数
    AioContext *ctx;             // 关联的 AioContext
    const char *scheduled;       // 调度来源（调试用）

    QSLIST_ENTRY(Coroutine) pool_next;       // 池化链表节点
    QSIMPLEQ_ENTRY(Coroutine) co_queue_next; // 队列节点
    QSIMPLEQ_HEAD(, Coroutine) co_queue_wakeup; // 唤醒列表
    QSLIST_ENTRY(Coroutine) co_scheduled_next;  // 调度列表节点
};
```

### 12.3 CoroutineAction 枚举

```c
// coroutine_int.h:38-42
typedef enum {
    COROUTINE_YIELD = 1,      // 协程主动让出
    COROUTINE_TERMINATE = 2,  // 协程执行完毕
    COROUTINE_ENTER = 3,      // 进入协程
} CoroutineAction;
```

### 12.4 后端实现

QEMU 协程的底层切换有三种后端：

| 后端 | 文件 | 机制 | 平台 |
|------|------|------|------|
| ucontext | `coroutine-ucontext.c` | `makecontext` + `sigsetjmp/siglongjmp` | Linux（默认） |
| sigaltstack | `coroutine-sigaltstack.c` | 信号栈 + 信号跳转 | 备选 POSIX |
| Windows Fiber | `coroutine-windows.c` | `CreateFiber` / `SwitchToFiber` | Windows |

栈大小：`COROUTINE_STACK_SIZE = 1MB`（`coroutine_int.h:36`）。

### 12.5 核心 API

```c
// 创建协程（qemu-coroutine.c:217-233）
Coroutine *qemu_coroutine_create(CoroutineEntry *entry, void *opaque);

// 进入/恢复协程
void qemu_coroutine_enter(Coroutine *co);

// 让出执行权（协程内调用）
void coroutine_fn qemu_coroutine_yield(void);
```

## 13. 协程池与生命周期

### 13.1 两级池化设计

协程创建/销毁开销较大（涉及栈分配），因此 QEMU 采用**全局池 + 线程本地池**的两级池化（`qemu-coroutine.c:28-67`）：

```
.-----------------------------------.
| Batch 1 | Batch 2 | Batch 3 | ... | global_pool（全局，QemuMutex 保护）
`-----------------------------------'

.-------------------.
| Batch 1 | Batch 2 | per-thread local_pool（TLS，无锁访问）
`-------------------'
```

### 13.2 池化生命周期

```c
// 创建：优先从池获取（qemu-coroutine.c:217-233）
Coroutine *qemu_coroutine_create(CoroutineEntry *entry, void *opaque)
{
    Coroutine *co = NULL;
    if (IS_ENABLED(CONFIG_COROUTINE_POOL)) {
        co = coroutine_pool_get();   // 优先从本地池 → 全局池获取
    }
    if (!co) {
        co = qemu_coroutine_new();   // 池中无可用 → 新建
    }
    co->entry = entry;
    co->entry_arg = opaque;
    return co;
}

// 终止后回收到池（qemu-coroutine.c:235-244）
static void coroutine_delete(Coroutine *co)
{
    co->caller = NULL;
    if (IS_ENABLED(CONFIG_COROUTINE_POOL)) {
        coroutine_pool_put(co);      // 回收到本地池 → 全局池
    } else {
        qemu_coroutine_delete(co);   // 直接释放
    }
}
```

## 14. CoMutex 与 CoQueue

### 14.1 CoMutex

`CoMutex` 是协程专用的互斥锁，当锁被占用时**让出协程**而不是阻塞线程（`coroutine.h:49-70`）：

```c
struct CoMutex {
    unsigned locked;        // 0=空闲, ≥1=有持有者/等待者
    AioContext *ctx;        // 持有锁的协程所在的 AioContext
    Coroutine *holder;      // 当前持有者

    // 无锁等待队列
    QSLIST_HEAD(, CoWaitRecord) from_push, to_pop;
    unsigned handoff, sequence;
};
```

实现在 `qemu-coroutine-lock.c:236-330`。当锁被占用时，等待的协程被挂起（yield），持有者释放锁时唤醒下一个等待者。

### 14.2 CoQueue

`CoQueue` 是协程条件等待队列（`coroutine.h:95-97`）：

```c
typedef struct CoQueue {
    QSIMPLEQ_HEAD(, Coroutine) entries;
} CoQueue;
```

核心操作（`qemu-coroutine-lock.c:41-115`）：

| 操作 | 作用 |
|------|------|
| `qemu_co_queue_wait(queue, lock)` | 释放锁并挂起协程，被唤醒后重新获取锁 |
| `qemu_co_queue_next(queue)` | 唤醒队列中的下一个协程 |
| `qemu_co_queue_restart_all(queue)` | 唤醒所有等待的协程 |

## 15. 协程与 AioContext 集成

### 15.1 协程调度

协程通过 AioContext 进行跨线程调度：

```c
// 在指定 AioContext 上调度协程（async.c:629-712）
void aio_co_schedule(AioContext *ctx, Coroutine *co);

// 在指定 AioContext 上进入协程
void aio_co_enter(AioContext *ctx, Coroutine *co);

// 唤醒协程（可跨线程）
void aio_co_wake(Coroutine *co);
```

### 15.2 qemu_aio_coroutine_enter()

这是协程执行的核心入口（`qemu-coroutine.c:246-312`）：

```c
void qemu_aio_coroutine_enter(AioContext *ctx, Coroutine *co)
{
    // 1. 设置协程的 AioContext
    co->ctx = ctx;

    // 2. 切换到协程执行
    switch (qemu_coroutine_switch(from, co, COROUTINE_ENTER)) {
    case COROUTINE_YIELD:
        // 协程 yield 了，稍后恢复
        break;
    case COROUTINE_TERMINATE:
        // 协程完成，回收到池
        coroutine_delete(co);
        break;
    }

    // 3. 处理协程的 co_queue_wakeup 列表
    // （协程可能在退出时请求唤醒其他等待的协程）
}
```

### 15.3 协程 BH（Bottom Half）

协程调度通过 BH 与 AioContext 事件循环集成。`aio_co_schedule()` 内部通过 `qemu_bh_schedule` 将协程恢复注册为 BH 回调（`async.c:527-550`）。

## 17. Bottom Half（BH）机制

### 17.1 概念

BH 是 QEMU 的延迟回调机制，类似 Linux 内核的 tasklet。BH 被调度后，在下一次 `aio_poll()` / `main_loop_wait()` 时执行。

### 17.2 API

```c
// 创建 BH
QEMUBH *qemu_bh_new(QEMUBHFunc *cb, void *opaque);
QEMUBH *aio_bh_new(AioContext *ctx, QEMUBHFunc *cb, void *opaque);

// 调度执行
void qemu_bh_schedule(QEMUBH *bh);

// 一次性 BH（执行后自动删除）
void aio_bh_schedule_oneshot(AioContext *ctx, QEMUBHFunc *cb, void *opaque);
```

实现在 `util/async.c:42-142`。

### 17.3 BH vs 定时器 vs 协程

| 机制 | 执行时机 | 适用场景 |
|------|---------|---------|
| BH | 下次事件循环迭代 | 延迟处理、中断下半部 |
| 定时器 | 指定时间后 | 超时、周期性任务 |
| 协程 | 异步等待完成后恢复 | I/O 操作、复杂异步流程 |

## 18. 线程间同步模式总结

### 18.1 同步机制对比

| 机制 | 适用场景 | 开销 | 读写特性 |
|------|---------|------|---------|
| **BQL** | 全局共享状态 | 高（全局串行化） | 读写互斥 |
| **RCU** | 读多写少的共享数据 | 读侧零开销 | 读无锁，写需 grace period |
| **CoMutex** | 协程间互斥 | 低（仅 yield/resume） | 协程级互斥 |
| **QemuMutex** | 线程间互斥 | 中 | 标准互斥锁 |
| **qatomic_*()** | 简单原子变量 | 最低 | 无锁原子操作 |

### 18.2 典型使用模式

```
场景 1: 设备 MMIO 处理
    vCPU 线程 → bql_lock() → device_read/write() → bql_unlock()

场景 2: 内存拓扑读取（热路径）
    vCPU 线程 → rcu_read_lock() → qatomic_rcu_read(flatview) → rcu_read_unlock()

场景 3: 内存拓扑更新（冷路径）
    主线程(BQL) → 构建新 FlatView → qatomic_rcu_set() → call_rcu(释放旧 view)

场景 4: 块层 I/O
    IOThread → 创建协程 → bdrv_co_preadv() → yield → 驱动完成 → wake → 返回

场景 5: vCPU 执行客户机代码
    vCPU 线程 → bql_unlock() → cpu_exec()/KVM_RUN → bql_lock()
```

### 20.2 核心要点

1. **BQL 是全局串行锁**，非递归，保护所有主循环可见的共享状态
2. **vCPU 线程在执行客户机代码时释放 BQL**，允许其他线程并发工作
3. **主循环在 poll 阻塞时释放 BQL**，vCPU 可在此期间处理 MMIO
4. **IOThread 有独立 AioContext**，可不经 BQL 处理块设备 I/O
5. **RCU 用于读多写少的数据**（FlatView、RAMBlock），读侧完全无锁
6. **`call_rcu()` 有专用线程**，在 grace period 后在 BQL 下执行回收回调
7. **协程用于块层 I/O**，以同步风格实现异步操作，避免回调地狱
8. **协程池采用两级设计**（全局 + TLS 本地），减少创建/销毁开销
9. **CoMutex/CoQueue 是协程感知的同步原语**，阻塞时 yield 而非阻塞线程
10. **AioContext 是事件循环抽象**，集成 fd 事件、BH、定时器和协程调度
