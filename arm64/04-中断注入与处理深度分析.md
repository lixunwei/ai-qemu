## 第一部分：TCG 模式中断注入全路径

### §1 端到端流程总览

TCG 模式下一个外部中断（如 SPI）从设备到 Guest 处理的完整路径：

```
设备驱动                 GICv3 内部                    ARM64 CPU
   │                        │                            │
   ├─qemu_set_irq()         │                            │
   │                        │                            │
   ├────────────────► gicv3_set_irq()                    │
   │                  ├─ gicv3_dist_set_irq()            │
   │                  │    (SPI pending 锁存)             │
   │                  │                                  │
   │                  ├─ gicv3_update()                   │
   │                  │    ├─ gicv3_update_noirqset()     │
   │                  │    │    (扫描 SPI→计算每 CPU HPPI) │
   │                  │    ├─ gicv3_redist_update()       │
   │                  │    │    (扫描 SGI/PPI→更新 HPPI)   │
   │                  │    └─ gicv3_cpuif_update()        │
   │                  │         ├─ icc_hppi_can_preempt() │
   │                  │         ├─ Group→IRQ/FIQ 映射     │
   │                  │         └─ qemu_set_irq(parent_*) │
   │                  │                    │              │
   │                  │                    ▼              │
   │                  │           arm_cpu_set_irq()       │
   │                  │           ├─ cpu_interrupt()      │
   │                  │           │  (设置 interrupt_request)
   │                  │           │                       │
   │                  │           │    ┌─── cpu_exec_loop ◄┐
   │                  │           │    │                   │
   │                  │           ▼    ▼                   │
   │                  │    cpu_handle_interrupt()          │
   │                  │    ├─ arm_cpu_exec_interrupt()     │
   │                  │    │    ├─ arm_excp_unmasked()     │
   │                  │    │    ├─ arm_phys_excp_target_el()
   │                  │    │    └─ do_interrupt()          │
   │                  │    │         │                     │
   │                  │    │         ▼                     │
   │                  │    │  arm_cpu_do_interrupt_aarch64()
   │                  │    │  ├─ 保存 PSTATE→SPSR_ELx     │
   │                  │    │  ├─ 保存 PC→ELR_ELx          │
   │                  │    │  ├─ 设置新 PSTATE (DAIF mask) │
   │                  │    │  ├─ 计算 VBAR_ELx + offset   │
   │                  │    │  └─ env->pc = vector_addr    │
   │                  │    │                              │
   │                  │    │         Guest 异常处理        │
   │                  │    │         ├─ 读 ICC_IAR1_EL1   │
   │                  │    │         │   (确认中断)        │
   │                  │    │         ├─ 执行 ISR           │
   │                  │    │         ├─ 写 ICC_EOIR1_EL1  │
   │                  │    │         │   (结束中断)        │
   │                  │    │         └─ ERET 返回          │
```

### §2 设备触发中断：qemu_set_irq

设备通过 `qemu_set_irq()` 触发中断，这是一个通用的 GPIO 信号机制：

```c
// 示例：PL011 UART 触发中断
// hw/char/pl011.c
qemu_set_irq(s->irq, flags != 0);  // level-triggered
```

`qemu_set_irq()` 最终调用目标 IRQ handler 的回调函数。对于连接到 GIC 的设备 IRQ，回调函数是 `gicv3_set_irq()`。

连线建立过程（`hw/arm/virt.c:1228-1283`）：

```c
// virt.c:create_gic() 中完成设备 IRQ → GIC SPI 的连线
sysbus_connect_irq(busdev, i, qdev_get_gpio_in(gicdev, ppi_offset + i));
```

### §3 GICv3 外部中断入口：gicv3_set_irq

**源文件**：`arm_gicv3.c:372-399`

```c
static void gicv3_set_irq(void *opaque, int irq, int level)
{
    GICv3State *s = opaque;

    if (irq < GIC_INTERNAL * s->num_cpu) {
        // PPI：私有外设中断，路由到特定 CPU
        int cpu = irq / GIC_INTERNAL;
        int ppiirq = irq % GIC_INTERNAL;
        // → gicv3_redist_set_irq()
    } else {
        // SPI：共享外设中断
        gicv3_dist_set_irq(s, irq, level);
    }
}
```

GPIO 输入注册在 `arm_gicv3.c:450-452`：
```c
qdev_init_gpio_in(dev, gicv3_set_irq,
                   GIC_INTERNAL * s->num_cpu + s->num_irq - GIC_INTERNAL);
```

### §4 Distributor SPI 锁存

**源文件**：`arm_gicv3_dist.c:941-960`

SPI 中断的 pending 状态由 Distributor 管理，支持两种触发模式：

| 触发模式 | 行为 | 配置寄存器 |
|---------|------|-----------|
| Level-triggered | pending 跟随输入电平 | `GICD_ICFGR` bit=0 |
| Edge-triggered | 仅在 0→1 跳变时锁存 pending | `GICD_ICFGR` bit=1 |

```c
static void gicv3_dist_set_irq(GICv3State *s, int irq, int level)
{
    // Edge-triggered：仅在上升沿锁存
    if (level == test_bit(...)) return;  // 无变化
    if (level) {
        // 0→1 跳变：设置 pending
        gicv3_gicd_pending_set(s, irq);
    }
    // Level-triggered：pending 由 gicd_int_pending() 实时检查输入电平
}
```

### §5 HPPI 级联计算链

中断状态改变后，需要重新计算每个 CPU 的最高优先级待处理中断（HPPI）。

**核心级联**（`arm_gicv3.c:257-357`）：

```
gicv3_update(s, irq, nlevel)          ← 入口，irq 指定变化的中断
  └─ gicv3_update_noirqset(s)         ← 全局 SPI 扫描
       │  遍历所有 SPI (irq=32..1019)
       │  对每个 SPI:
       │    ├─ gicd_int_pending(s, irq)  检查是否 pending
       │    ├─ 检查 enable、group、路由
       │    └─ irqbetter(): 与当前 HPPI 比优先级
       │  结果写入 cs->hppi (irq, prio, grp, nmi)
       │
       ├─ gicv3_redist_update_noirqset(cs)   ← 每 CPU 的 SGI/PPI
       │    遍历 irq=0..31
       │    与 Distributor HPPI 比较，取更高优先级
       │
       └─ gicv3_cpuif_update(cs)             ← CPU Interface 决策
            判断是否可抢占 → 映射 IRQ/FIQ → 断言信号线
```

`gicv3_full_update_noirqset()`（`arm_gicv3.c:335-357`）在全局状态变化时（如 GICD_CTLR 写入）执行完整重计算。

### §6 CPU Interface 更新：gicv3_cpuif_update

**源文件**：`arm_gicv3_cpuif.c:1046-1101`

这是 GICv3 中断注入的**核心决策函数**，决定是否向 CPU 断言 IRQ/FIQ 信号：

```c
void gicv3_cpuif_update(GICv3CPUState *cs)
{
    int irqlevel = 0, fiqlevel = 0, nmilevel = 0;

    // 步骤1：G1S→G0 降级（无 EL3 的 CPU）
    if (cs->hppi.grp == GICV3_G1 && !arm_feature(env, ARM_FEATURE_EL3)) {
        cs->hppi.grp = GICV3_G0;
    }

    // 步骤2：抢占检查
    if (icc_hppi_can_preempt(cs)) {
        // 步骤3：Group→IRQ/FIQ 映射
        bool isfiq = ...;  // 见 §8
        if (isfiq) fiqlevel = 1;
        else if (cs->hppi.nmi) nmilevel = 1;
        else irqlevel = 1;
    }

    // 步骤4：断言 CPU 输入线
    qemu_set_irq(cs->parent_fiq, fiqlevel);  // → ARM_CPU_FIQ
    qemu_set_irq(cs->parent_irq, irqlevel);  // → ARM_CPU_IRQ
    qemu_set_irq(cs->parent_nmi, nmilevel);  // → ARM_CPU_NMI
}
```

### §7 抢占判定：icc_hppi_can_preempt

**源文件**：`arm_gicv3_cpuif.c:993-1044`

```
icc_hppi_can_preempt(cs)
  │
  ├─ icc_no_enabled_hppi(cs)?     → 无有效 pending 中断，返回 false
  │
  ├─ NMI 中断特殊检查:
  │    ├─ G1NS NMI 且 PMR < 0x80  → 被掩码，返回 false
  │    └─ Secure 态且 PMR == 0x80 → 被掩码，返回 false
  │
  ├─ 普通中断: hppi.prio >= PMR?  → 被优先级掩码屏蔽，返回 false
  │
  ├─ rprio = icc_highest_active_prio(cs)
  │    └─ rprio == 0xff?          → 无活动中断，可抢占，返回 true
  │
  ├─ mask = icc_gprio_mask(cs, grp)  ← 由 BPR 决定组优先级掩码
  │
  └─ (hppi.prio & mask) < (rprio & mask)?
       ├─ true  → 可抢占当前活动中断
       └─ false → NMI 再检查：同优先级组且无 NMI 活动 → 可抢占
```

**关键概念**：
- **PMR**（Priority Mask Register）：`ICC_PMR_EL1`，只有优先级数值**低于**（数值更小 = 更高优先级）PMR 的中断才能通过
- **BPR**（Binary Point Register）：将优先级分为组优先级和子优先级，抢占只看组优先级
- **APR**（Active Priority Register）：记录当前所有活动中断的优先级层级

### §8 Group→IRQ/FIQ 映射规则

**源文件**：`arm_gicv3_cpuif.c:1073-1094`

GICv3 中断分为三组，映射到不同的 CPU 异常线：

| 中断组 | Secure 态 CPU | Non-Secure 态 CPU | AArch64 EL3 |
|-------|--------------|-------------------|-------------|
| Group 0 | **FIQ** | **FIQ** | **FIQ** |
| Group 1 (Secure) | IRQ | **FIQ** | IRQ |
| Group 1 Non-Secure | **FIQ** | IRQ | IRQ |

核心逻辑：

```c
switch (cs->hppi.grp) {
case GICV3_G0:
    isfiq = true;              // G0 总是 FIQ
    break;
case GICV3_G1:                 // G1 Secure
    isfiq = (!arm_is_secure(env) ||
             (cur_el == 3 && arm_el_is_aa64(env, 3)));
    break;
case GICV3_G1NS:              // G1 Non-Secure
    isfiq = arm_is_secure(env); // Secure 看 NS 中断 → FIQ（信号交叉）
    break;
}
```

**设计原理**：FIQ 用于将中断路由到更高特权级别。当 Secure 态收到 Non-Secure 中断时使用 FIQ 以触发 SCR_EL3.FIQ 路由到 EL3。

### §9 qemu_irq 连线：GIC 输出→CPU 输入

```c
for (irq = 0; irq < s->smp_cpus; irq++) {
    DeviceState *cpudev = DEVICE(qemu_get_cpu(irq));
```

### §10 arm_cpu_set_irq：设置 interrupt_request

**源文件**：`cpu.c:781-833`

CPU 的 GPIO 输入处理函数，将 GIC 输出的电平信号转换为 `interrupt_request` 位：

```c
static void arm_cpu_set_irq(void *opaque, int irq, int level)
{
    ARMCPU *cpu = opaque;
    CPUState *cs = CPU(cpu);

    switch (irq) {
    case ARM_CPU_IRQ:
        if (level) {
            cpu_interrupt(cs, CPU_INTERRUPT_HARD);
        } else {
            cpu_reset_interrupt(cs, CPU_INTERRUPT_HARD);
        }
        break;
    case ARM_CPU_FIQ:
        if (level) cpu_interrupt(cs, CPU_INTERRUPT_FIQ);
        else cpu_reset_interrupt(cs, CPU_INTERRUPT_FIQ);
        break;
    case ARM_CPU_VIRQ:
        // VIRQ 有特殊合成逻辑（§25）
        env->irq_line_state |/&= CPU_INTERRUPT_VIRQ;
        arm_cpu_update_virq(cpu);
        break;
    // ... VFIQ, NMI, VINMI, VFNMI 类似
    }
}
```

`cpu_interrupt()` 设置 `cs->interrupt_request` 位，并通过 `qemu_cpu_kick()` 唤醒可能处于 WFI 的 vCPU 线程。

GPIO 注册（`cpu.c:1203`）：
```c
qdev_init_gpio_in(DEVICE(cpu), arm_cpu_set_irq, 6);
// 6 个输入: IRQ, FIQ, VIRQ, VFIQ, NMI, VINMI(+VFNMI 共用)
```

## 第二部分：TCG 中断检查与异常进入

### §11 cpu_exec_loop 中断检查点

**源文件**：`cpu-exec.c:777-856`

在 TCG 主循环中，每次 TB 执行**之前**都会检查 pending 中断：

```
cpu_exec_loop (cpu-exec.c:932)
  │
  ├─ 步骤1: 检查异常（exception_index >= 0）
  │    └─ cpu_handle_exception() → 处理同步异常
  │
  ├─ 步骤2: 检查中断 ◄── 中断检查点
  │    └─ cpu_handle_interrupt()
  │         │
  │         ├─ interrupt_request & CPU_INTERRUPT_HALT → halt
  │         │
  │         ├─ interrupt_request 有任何位?
  │         │    └─ cc->tcg_ops->cpu_exec_interrupt(cs, interrupt_request)
  │         │       即 arm_cpu_exec_interrupt() ← ARM64 实现
  │         │       └─ 返回 true → 中断被接受，跳到步骤1 处理异常
  │         │
  │         └─ exit_request?
  │              └─ 退出 cpu_exec
  │
  ├─ 步骤3: TB 查找 (tb_lookup)
  ├─ 步骤4: TB 执行 (cpu_loop_exec_tb)
  └─ 步骤5: TB 链接 → 回到步骤1
```

**关键点**：`cpu_interrupt()` 设置 `exit_request=1` 导致当前 TB 提前退出（通过 `icount_decr.u16.high` 或异步安全退出），从而在下一轮迭代中检查中断。

### §12 arm_cpu_exec_interrupt：优先级扫描

**源文件**：`cpu-irq.c:171-274`

ARM64 中断按**固定优先级顺序**扫描，第一个未屏蔽的中断被接受：

```
arm_cpu_exec_interrupt(cs, interrupt_request)
  │
  │  NMI 特性启用时:
  ├─ 1. CPU_INTERRUPT_NMI   → EXCP_NMI   (物理 NMI)
  ├─ 2. CPU_INTERRUPT_VINMI → EXCP_VINMI (虚拟 NMI IRQ)
  ├─ 3. CPU_INTERRUPT_VFNMI → EXCP_VFNMI (虚拟 NMI FIQ)
  │
  │  NMI 特性未启用时:
  │  NMI → 降级为 HARD, VINMI → VIRQ, VFNMI → VFIQ
  │
  │  标准优先级顺序:
  ├─ 4. CPU_INTERRUPT_FIQ   → EXCP_FIQ   (物理 FIQ)
  ├─ 5. CPU_INTERRUPT_HARD  → EXCP_IRQ   (物理 IRQ)
  ├─ 6. CPU_INTERRUPT_VIRQ  → EXCP_VIRQ  (虚拟 IRQ)
  ├─ 7. CPU_INTERRUPT_VFIQ  → EXCP_VFIQ  (虚拟 FIQ)
  └─ 8. CPU_INTERRUPT_VSERR → EXCP_VSERR (虚拟 SError)

  每个中断:
    target_el = arm_phys_excp_target_el(excp_idx)
    if arm_excp_unmasked(excp_idx, target_el):
        cs->exception_index = excp_idx
        env->exception.target_el = target_el
        do_interrupt(cs)    // → arm_cpu_do_interrupt()
        return true
```

**优先级顺序**：NMI > FIQ > IRQ > VIRQ > VFIQ > VSERR

### §13 arm_excp_unmasked：PSTATE 掩码检查

**源文件**：`cpu-irq.c:15-168`

此函数判断指定异常类型在当前 CPU 状态下是否**未被屏蔽**：

```
arm_excp_unmasked(cs, excp_idx, target_el, cur_el, secure, hcr_el2)
  │
  ├─ cur_el > target_el?  → false (不能向下级EL递送)
  │
  ├─ ALLINT 检查 (FEAT_NMI):
  │    allIntMask = PSTATE.ALLINT ||
  │                 (SCTLR.SPINTMASK && PSTATE.SP)
  │
  ├─ 按异常类型分支:
  │    ├─ EXCP_NMI:    pstate_unmasked = !allIntMask
  │    ├─ EXCP_VINMI:  需要 HCR.IMO && !TGE
  │    ├─ EXCP_VFNMI:  需要 HCR.FMO && !TGE
  │    ├─ EXCP_FIQ:    pstate_unmasked = !(PSTATE.F) && !allIntMask
  │    ├─ EXCP_IRQ:    pstate_unmasked = !(PSTATE.I) && !allIntMask
  │    ├─ EXCP_VIRQ:   需要 HCR.IMO && !TGE; pstate_unmasked = !(PSTATE.I)
  │    ├─ EXCP_VFIQ:   需要 HCR.FMO && !TGE; pstate_unmasked = !(PSTATE.F)
  │    └─ EXCP_VSERR:  需要 HCR.AMO && !TGE; pstate_unmasked = !(PSTATE.A)
  │
  ├─ 跨 EL 覆盖规则 (target_el > cur_el):
  │    ├─ 从 EL0 到高 EL: 总是 unmasked（PSTATE 掩码不起作用）
  │    └─ 从 ELn 到更高 EL: superpriority 中断可覆盖掩码
  │
  └─ return unmasked || pstate_unmasked
```

**PSTATE.DAIF 各位**：
| 位 | 名称 | 屏蔽的异常 |
|---|------|----------|
| D | Debug | Debug 异常 |
| A | SError | 异步 SError |
| I | IRQ | IRQ 和 VIRQ |
| F | FIQ | FIQ 和 VFIQ |

### §14 arm_phys_excp_target_el：目标 EL 查表

**源文件**：`helper.c:8310-8420`

使用 ARM ARM G1.13.4 规定的 6 维查找表确定异常目标 EL：

```c

//                |     |    |   |     |       |
//                |     |    |   |     |       └── 当前 EL (0-3)
//                |     |    |   |     └────────── Secure(1)/NS(0)
//                |     |    |   └──────────────── HCR 路由位
//                |     |    └──────────────────── SCR.RW
//                |     └───────────────────────── SCR 路由位
//                └─────────────────────────────── EL3 是否 64 位
```

**路由控制位**：

| 异常类型 | SCR_EL3 路由位 | HCR_EL2 路由位 | 效果 |
|---------|---------------|---------------|------|
| IRQ/NMI | `SCR_EL3.IRQ` | `HCR_EL2.IMO` | 路由到 EL3/EL2 |

**常见场景**：
- 裸机（无 EL2/EL3）：IRQ → EL1
- Type-1 Hypervisor（HCR.IMO=1）：Guest EL1 的 IRQ → EL2

当 `do_interrupt()` 被调用后，最终进入此函数执行 AArch64 异常进入序列：

### §16 向量表偏移计算

**源文件**：`helper.c:9217-9337`

AArch64 向量表基于 `VBAR_ELx`，偏移由**来源**和**异常类型**决定：

```
VBAR_ELx
  │
  ├─ +0x000  同 EL, SP_EL0    ──┬── +0x000 Synchronous
  │                              ├── +0x080 IRQ/vIRQ/NMI/vNMI
  │                              ├── +0x100 FIQ/vFIQ/vFNMI
  │                              └── +0x180 SError/vSError
  │
  ├─ +0x200  同 EL, SP_ELx    ──┬── +0x200 Synchronous
  │                              ├── +0x280 IRQ
  │                              ├── +0x300 FIQ
  │                              └── +0x380 SError
  │
  ├─ +0x400  低 EL, AArch64   ──┬── +0x400 Synchronous
  │                              ├── +0x480 IRQ
  │                              ├── +0x500 FIQ
  │                              └── +0x580 SError
  │
  └─ +0x600  低 EL, AArch32   ──┬── +0x600 Synchronous
                                 ├── +0x680 IRQ
                                 ├── +0x700 FIQ
                                 └── +0x780 SError
```

**QEMU 实现的偏移计算**：

```c
// 1. 来源偏移（helper.c:9217-9251）
if (cur_el < new_el) {
    addr += is_aa64 ? 0x400 : 0x600;  // 低 EL
} else {
    if (PSTATE & PSTATE_SP)
        addr += 0x200;                 // 同 EL, SP_ELx
    // else: 同 EL, SP_EL0 → 无偏移
}

// 2. 异常类型偏移（helper.c:9322-9337）
case EXCP_IRQ/VIRQ/NMI/VINMI:  addr += 0x080;
case EXCP_FIQ/VFIQ/VFNMI:     addr += 0x100;
case EXCP_VSERR:               addr += 0x180;
// Synchronous: 无额外偏移
```

**典型场景**：EL0 运行用户态，IRQ 路由到 EL1，SP 使用 SP_EL1：
- 来源偏移：`+0x400`（低 EL, AArch64）
- 类型偏移：`+0x080`（IRQ）
- 最终地址：`VBAR_EL1 + 0x480`

## 第三部分：Guest 中断处理与 EOI

### §18 Guest 异常向量入口

当 QEMU 完成异常进入（§15），`env->pc` 指向向量表中的 IRQ 入口。Guest 内核的典型处理流程（以 Linux 为例）：

```
IRQ 向量入口 (VBAR_EL1 + offset)
  │
  ├─ 保存通用寄存器到栈 (kernel_entry 宏)
  │    x0-x30, SP, PC(ELR), PSTATE(SPSR)
  │
  ├─ 读 ICC_IAR1_EL1            ← 确认中断（QEMU 模拟）
  │    返回中断 ID (INTID)
  │
  ├─ 查找 IRQ handler (irq_desc[INTID])
  │    └─ 调用设备驱动的 ISR
  │
  ├─ 写 ICC_EOIR1_EL1 = INTID   ← 结束中断（QEMU 模拟）
  │
  ├─ 恢复通用寄存器
  │
  └─ ERET                        ← 从异常返回
       ├─ PC = ELR_EL1
       ├─ PSTATE = SPSR_EL1
       └─ 继续被中断的指令
```

在 QEMU TCG 模式下，Guest 对 `ICC_IAR1_EL1` 和 `ICC_EOIR1_EL1` 的访问会触发系统寄存器陷入（trap），由 QEMU 的 GICv3 CPU Interface 模拟代码处理。

### §19 ICC_IAR1_EL1 读取：中断确认

### §20 icc_activate_irq：状态迁移

**源文件**：`arm_gicv3_cpuif.c:1158-1187`

中断确认后的状态迁移：**Pending → Active**

```c
static void icc_activate_irq(GICv3CPUState *cs, int irq)
{
    // 1. 更新 Active Priority Register (APR)
    uint32_t mask = icc_gprio_mask(cs, cs->hppi.grp);
    int prio = cs->hppi.prio & mask;
    int aprbit = prio >> (8 - cs->prebits);
    cs->icc_apr[cs->hppi.grp][regno] |= (1U << regbit);

    // 2. 根据中断类型更新状态
    if (irq < GIC_INTERNAL) {
        // SGI/PPI: Redistributor 管理
        cs->gicr_iactiver0 |= bit;    // 设置 Active
        cs->gicr_ipendr0 &= ~bit;     // 清除 Pending
        gicv3_redist_update(cs);       // 重新计算 HPPI
    } else if (irq < GICV3_LPI_INTID_START) {
        // SPI: Distributor 管理
        gicv3_gicd_active_set(s, irq);
        gicv3_gicd_pending_clear(s, irq);
        gicv3_update(s, irq, 1);       // 重新计算 HPPI
    } else {
        // LPI: 清除 pending table 中的 bit
        gicv3_redist_lpi_pending(cs, irq, 0);
    }
}
```

**关键效果**：
1. APR 记录新的活动优先级 → 阻止同优先级组的后续中断抢占
2. 清除 Pending 位 → 此中断不再参与 HPPI 计算
3. 触发 `gicv3_update()` → 重新扫描下一个最高优先级中断 → 可能断言或撤销 IRQ/FIQ 线

### §21 ICC_EOIR1_EL1 写入：中断结束

**源文件**：`arm_gicv3_cpuif.c:1645-1714`

```c
{
    int irq = value & 0xffffff;

    // 虚拟化检查

    // 验证 EOI 的 Group 与当前 EOIR 寄存器匹配（EOIR0→G0, EOIR1→G1/G1NS）
    // 安全状态检查...

    icc_drop_prio(cs, grp);
```

### §22 优先级下降与去激活

EOI 操作分为两步，可以合并也可以分离（`ICC_CTLR_EL1.EOImode`）：

**步骤1：Priority Drop（`icc_drop_prio`）**
- 清除 APR 中最高活动优先级位
- 效果：降低 running priority，允许同优先级或更低优先级的中断抢占

**步骤2：Deactivation（`icc_deactivate_irq`）**
- 清除中断的 Active 位
- SPI：清除 `GICD_ISACTIVER` 对应位
- SGI/PPI：清除 `GICR_ISACTIVER0` 对应位

**EOImode 分离模式**（`ICC_CTLR_EL1.EOImode=1`）：
- `ICC_EOIR1_EL1` 写入只做 Priority Drop
- 需要额外写 `ICC_DIR_EL1` 完成 Deactivation
- 用途：Hypervisor 可以在 Priority Drop 后注入虚拟中断，延迟物理中断的 Deactivation

```
正常 EOI 流程:
  ICC_EOIR1_EL1 写入
    ├─ icc_drop_prio()       → APR 清除，running priority 下降
    └─ icc_deactivate_irq()  → Active 位清除
        └─ gicv3_update()    → 重新计算 HPPI → 可能触发下一个中断

分离 EOI 流程:
  ICC_EOIR1_EL1 写入
    └─ icc_drop_prio()       → APR 清除
  ... Guest 处理其他事务 ...
  ICC_DIR_EL1 写入
    └─ icc_deactivate_irq()  → Active 位清除
```

## 第四部分：虚拟中断注入（EL2→EL1）

### §23 虚拟中断概述

GICv3 的虚拟中断机制允许 Hypervisor（EL2）向 Guest OS（EL1）注入中断，无需 Guest 感知虚拟化的存在。

**硬件机制**：
- Hypervisor 写 `ICH_LR<n>_EL2` List Register 描述虚拟中断
- CPU 在 EL1 看到虚拟中断通过 VIRQ/VFIQ 线
- Guest EL1 读写 `ICC_*` 寄存器时，HCR_EL2.IMO/FMO 使其自动重定向到 `ICV_*` 虚拟寄存器

**QEMU 模拟**：完全在软件中实现 ICH/ICV 寄存器和虚拟中断分发逻辑。

### §26 ICV 寄存器：Guest EL1 视角

**源文件**：`arm_gicv3_cpuif.c:800-842`（`icv_iar_read`），`arm_gicv3_cpuif.c:1584-1643`（`icv_eoir_write`）

当 `HCR_EL2.IMO=1` 时，Guest EL1 对 `ICC_*` 寄存器的访问被透明重定向到 `ICV_*` 处理函数：

| Guest 访问 | QEMU 实际调用 | 操作 |
|-----------|-------------|------|
| `ICC_IAR1_EL1` 读 | `icv_iar_read()` | 扫描 ICH_LR，返回最高优先级虚拟 INTID |
| `ICC_EOIR1_EL1` 写 | `icv_eoir_write()` | 虚拟优先级下降 + 去激活 LR |
| `ICC_PMR_EL1` 读/写 | `icv_pmr_read/write()` | 操作 `ICH_VMCR_EL2.VPMR` |
| `ICC_BPR1_EL1` 读/写 | `icv_bpr_read/write()` | 操作 `ICH_VMCR_EL2.VBPR1` |
| `ICC_HPPIR1_EL1` 读 | `icv_hppir_read()` | 返回虚拟 HPPI |

**ICV IAR 流程**（`icv_iar_read`）：

```
icv_iar_read()
  │
  ├─ 扫描 ICH_LR[0..n]，找 State=Pending 的最高优先级
  ├─ 检查虚拟 PMR 和虚拟 BPR 抢占
  ├─ LR State: Pending → Active (或 PendingActive)
  ├─ 更新虚拟 APR
  ├─ gicv3_cpuif_virt_irq_fiq_update()  → 重新评估 VIRQ/VFIQ
  └─ 返回 vINTID
```

### §27 Maintenance 中断

**源文件**：`arm_gicv3_cpuif.c:434-468`（`maintenance_interrupt_state`），`arm_gicv3_cpuif.c:526-558`（`gicv3_cpuif_virt_update`）

GICv3 虚拟接口在特定条件下向 Hypervisor 发送维护中断（Maintenance Interrupt），通知其需要介入管理虚拟中断状态。

**触发条件**（检查 `ICH_HCR_EL2` 使能位）：

| 条件标志 | 含义 | 触发时机 |
|---------|------|---------|
| `EOIcount` | EOI 计数溢出 | Guest 写 EOI 但无匹配 LR |
| `NPIE` | No Pending 中断使能 | 所有 LR 都不是 Pending |
| `LRENP` | LR Entry Not Present | LR 从有到空 |
| `U` | Underflow | 活动/待处理 LR 数 ≤ 1 |
| `VGrp0/1E/D` | 虚拟 Group 0/1 使能/禁用 | Group enable 状态变化 |

```c
static uint32_t maintenance_interrupt_state(GICv3CPUState *cs)
{
    uint32_t value = 0;
    // 检查 EOI count > 0
    if (cs->ich_hcr_el2 & ICH_HCR_EL2_EOICOUNT_MASK) {
        value |= ICH_MISR_EL2_EOI;
    }
    // 检查无 Pending 中断
    if (!(validcount - activecount) && (cs->ich_hcr_el2 & ICH_HCR_EL2_NPIE)) {
        value |= ICH_MISR_EL2_NP;
    }
    // ... 其他条件
    return value;
}
```

维护中断通过 PPI 线连接到 Hypervisor（`virt.c:1255-1264`），Hypervisor 收到后可以刷新 LR、注入新的虚拟中断。

## 第五部分：KVM 模式中断注入

### §28 KVM vGIC 架构概述

KVM 模式下，GICv3 在**Linux 内核**中实现（vGIC），QEMU 仅负责配置和特殊操作：

```
┌─────────────────────────────────────────────────────────┐
│                     QEMU 用户态                         │
│                                                         │
│  设备模型 ──→ KVM_IRQ_LINE / irqfd / KVM_SIGNAL_MSI    │
│                        │                                │
├────────────────────────┼────────────────────────────────┤
│                        ▼          Linux 内核            │
│                    KVM vGIC                             │
│                    ├─ vGICD (Distributor)               │
│                    ├─ vGICR (Redistributor)             │
│                    ├─ vICH (CPU Interface)              │
│                    └─ vITS (Interrupt Translation)      │
│                        │                                │
│                        ▼                                │
│                  自动注入到 vCPU                         │
│                  (无 VM Exit)                           │
│                        │                                │
├────────────────────────┼────────────────────────────────┤
│                        ▼          ARM64 硬件            │
│                   物理 GICv3                            │
│                   ICH_LR 直接编程                       │
│                   Guest 直接访问 ICC 寄存器              │
└─────────────────────────────────────────────────────────┘
```

**KVM vs TCG 的根本区别**：
- **TCG**：GICv3 完全在 QEMU 用户态软件模拟
- **KVM**：GICv3 在内核 vGIC 中实现，利用硬件 GICv3 的虚拟化扩展（ICH_LR），Guest 直接访问 ICC 寄存器无需 VM Exit

```c
    // 编码 IRQ 编号：
```

```
KVM:  device → qemu_set_irq → kvm_arm_gicv3_set_irq → ioctl(KVM_IRQ_LINE) → [内核 vGIC]
```

### §30 irqfd：零拷贝中断注入

**源文件**：`kvm-all.c:2448-2491`（`kvm_irqchip_assign_irqfd`），`kvm-all.c:2549-2559`（`kvm_irqchip_add_irqfd_notifier`）

irqfd 机制允许设备（如 VFIO passthrough 设备）通过 eventfd **直接**向内核 vGIC 注入中断，完全绕过 QEMU 用户态：

```
┌──────────┐    eventfd     ┌──────────┐    内核 vGIC    ┌──────────┐
│  设备/   │ ──────────────→│  KVM     │ ──────────────→│  vCPU    │
│  VFIO    │   (内核态直通)  │  irqfd   │   (无 VM Exit)  │  Guest   │
└──────────┘                └──────────┘                └──────────┘
```

```c
// 绑定 eventfd 到 KVM GSI
static int kvm_irqchip_assign_irqfd(KVMState *s,
                                     EventNotifier *event,
                                     EventNotifier *resample,
                                     int virq, bool assign)
{
    struct kvm_irqfd irqfd = {
        .fd = event_notifier_get_fd(event),
        .gsi = virq,
        .flags = assign ? 0 : KVM_IRQFD_FLAG_DEASSIGN,
    };
    // Resample fd 用于 level-triggered 中断的 re-injection
    if (resample) {
        irqfd.flags |= KVM_IRQFD_FLAG_RESAMPLE;
        irqfd.resamplefd = event_notifier_get_fd(resample);
    }
    return kvm_vm_ioctl(s, KVM_IRQFD, &irqfd);
}
```

**性能优势**：irqfd 路径完全在内核态完成，单次中断注入无需任何用户态/内核态切换。适用于高频中断场景（如 NVMe、高速网卡）。

### §32 内核态 vGIC 自动分发

KVM 内核 vGIC 的关键特性是**自动中断分发**，不需要 VM Exit：

1. **SPI 注入**：`KVM_IRQ_LINE` → vGIC 更新 Distributor → 计算目标 vCPU → 编程 ICH_LR → Guest 进入时自动可见
2. **ICC 寄存器**：Guest 读 `ICC_IAR1_EL1` / 写 `ICC_EOIR1_EL1` 由 ARM64 硬件直接处理（通过 ICH/ICV 硬件虚拟化），**不触发 VM Exit**
3. **WFI 处理**：vCPU 执行 WFI 时，若无 pending 中断则 VM Exit 到 KVM，KVM 将 vCPU 阻塞；新中断到达时唤醒 vCPU

**需要 VM Exit 的场景**：
- MMIO 访问（如 GICD/GICR 寄存器配置）
- ITS 命令队列操作
- vCPU WFI 且无 pending 中断
- 维护中断处理

## 第六部分：TCG vs KVM 对比与时序

### §34 全路径对比表

| 阶段 | TCG 路径 | KVM 路径 |
|------|---------|---------|
| **设备触发** | `qemu_set_irq()` | `qemu_set_irq()` |
| **GIC 入口** | `gicv3_set_irq()` (QEMU 用户态) | `kvm_arm_gicv3_set_irq()` → `ioctl(KVM_IRQ_LINE)` |
| **GIC 处理** | 软件模拟 GICD/GICR/CPUIF | 内核 vGIC (硬件辅助) |
| **HPPI 计算** | `gicv3_update()` 全软件扫描 | 内核态计算 |
| **CPU 信号** | `qemu_set_irq(parent_irq)` → `cpu_interrupt()` | 内核自动编程 ICH_LR |
| **中断检查** | `arm_cpu_exec_interrupt()` 每轮循环检查 | 硬件中断注入 (无 VM Exit) |
| **异常进入** | `arm_cpu_do_interrupt_aarch64()` 软件模拟 | ARM64 硬件自动异常进入 |
| **ICC_IAR 读** | `icc_iar1_read()` (MMIO trap) | 硬件 ICV 直接处理 (无 VM Exit) |
| **ISR 执行** | TCG 翻译执行 Guest 代码 | 原生执行 |
| **ICC_EOIR 写** | `icc_eoir_write()` (MMIO trap) | 硬件 ICV 直接处理 (无 VM Exit) |
| **性能** | 每个中断 ~数千宿主指令 | 多数情况 0 VM Exit |
