# ARM64 指令集模拟规范验证：DDI 0487 M.b Chapter C3 / C6 与 QEMU 对照分析

## 1. 概述

本文目标是把既有三份分析文档与 **ARM Architecture Reference Manual for A-profile architecture, DDI 0487 M.b** 的 **Chapter C3（Branches / Exception generating / System instructions）**、**Chapter C6（A64 base instructions）** 逐项对照，并进一步核验当前 QEMU 源码中的 AArch64 TCG 翻译实现是否与规范描述一致。

**核验对象**：
- 既有文档：
  - `darren/arm64/02-特殊指令模拟深度分析.md`
  - `darren/arm64/07-不同EL下指令执行差异深度分析.md`
  - `darren/arm64/32-ARM64特殊系统寄存器与Cache-AT指令深度分析.md`
- QEMU 源码：
  - `target/arm/tcg/a64.decode`
  - `target/arm/tcg/translate-a64.c`
  - `target/arm/tcg/cpregs-at.c`
  - `target/arm/tcg/op_helper.c`
  - `target/arm/helper.c`

**核验范围**：
1. 分支指令：`B/BL/BR/BLR/RET/B.cond/CBZ/CBNZ/TBZ/TBNZ`
2. 异常生成指令：`SVC/HVC/SMC/BRK/HLT/ERET`
3. 系统指令：`MRS/MSR/SYS/SYSL`，barrier，cache maintenance，`AT/TLBI`
4. 基础数据处理：`ADD/SUB`、逻辑、bitfield、extract、conditional select
5. 基础加载存储：`LDR/STR/LDP/STP`、exclusive、LSE atomic

**重要结论先行**：
- 规范层面，QEMU 当前实现与 **DDI 0487 §C3.1 / §C3.1.5 / §C6.1 / §C6.2** 的主干语义整体一致。
- 但 QEMU 在若干点上做了**实现折叠或简化**：
  - `DMB` 与 `DSB` 在 TCG 中统一映射为 `tcg_gen_mb()`，不区分硬件级“完成”语义。
  - `WFE` 在部分路径上被实现为“可让出执行/近似 NOP”，不模拟真实事件寄存器。
  - `LDXR/STXR` 采用“记录地址和值 + cmpxchg”的软件独占监视器近似，而非硬件规范的完整 monitor 模型。
  - 大多数 `DC/IC` 指令在 system-mode 下是 `NOP/trap-only`；`IC IVAU` 的 TB 失效主要体现在 `CONFIG_USER_ONLY`。
- 既有文档 02/07/32 整体质量较高，但存在 **1 处明显错误** 与 **2 处过度概括**，见第 8 节。

另一个值得说明的点是：用户指定的 `disas_uncond_b_imm`、`disas_system`、`disas_exc` 在**当前** QEMU 树中已经不是主路径。当前实现采用 **decodetree (`a64.decode`) + `trans_*` 翻译函数** 模式，对应职责已分散到 `trans_B/trans_BL/trans_SYS/trans_SVC/...` 等函数中。

## 2. 分支指令验证（§C3.1.1 - §C3.1.5）

### 2.1 规范基线

DDI 0487 将分支类指令拆分为：
- **Conditional branch**：`B.cond`、`CBZ/CBNZ`、`TBZ/TBNZ`（§C3.1.1）
- **Unconditional branch (immediate)**：`B/BL`（§C3.1.2）
- **Unconditional branch (register)**：`BR/BLR/RET`（§C3.1.3）
- **Direct and indirect branch**：把直接/间接分支再重新分组（§C3.1.4）
- **Exception generation and return**：`SVC/HVC/SMC/BRK/HLT/ERET`（§C3.1.5）

其中：
- `BL` 必须把 `PC+4` 写入 `X30`（DDI 0487 §C3.1.2，§C6.2.43）。
- `RET` 在行为上与 `BR` 类似，但向处理器提供“这是返回”提示（DDI 0487 §C3.1.3）。
- `CBZ/CBNZ/TBZ/TBNZ` 属于“比较/测试并分支”，不是普通条件码分支（DDI 0487 §C3.1.1，§C3.1.4）。

### 2.2 QEMU decode tree 对照

`a64.decode` 中的对应编码与规范分类一一对应：

```text
# target/arm/tcg/a64.decode
B    0 00101 ..........................     # 行 194
BL   1 00101 ..........................     # 行 195
CBZ  sf:1 011010 nz:1 ...................   # 行 200
TBZ  . 011011 nz:1 ..... ..............     # 行 206
B.cond 0101010 0 ...................         # 行 209
BR   1101011 0000 11111 000000 rn:5 00000   # 行 211
BLR  1101011 0001 11111 000000 rn:5 00000   # 行 212
RET  1101011 0010 11111 000000 rn:5 00000   # 行 213
ERET 1101011 0100 11111 000000 11111 00000  # 行 226
```

可见 decode tree 已直接按 ARM ARM 的编码分类命名；这也是当前 QEMU 取代旧式 `disas_uncond_b_imm()` 的关键证据。

### 2.3 `B/BL`：立即数分支

**规范**：
- `B`：PC-relative，无条件跳转，范围 ±128MB（DDI 0487 §C3.1.2）。
- `BL`：同样是 PC-relative，但需要写 `X30 = PC+4`（DDI 0487 §C6.2.43）。

**QEMU 实现**：`translate-a64.c:1697-1716`

```c
static bool trans_B(...) {
    reset_btype(s);
    gen_goto_tb(s, 0, a->imm);
}

static bool trans_BL(...) {
    gen_pc_plus_diff(s, link, 4);
    tcg_gen_mov_i64(cpu_reg(s, 30), link);
    reset_btype(s);
    gen_goto_tb(s, 0, a->imm);
}
```

**结论**：✓ 与规范一致。
- `a->imm` 已在 decode 阶段通过 `%imm26 !function=times_4` 还原为 **imm26 << 2**，吻合规范的 `SignExtend(imm26:'00')`。
- `BL` 明确写回 `X30`。
- 当前实现还附加了 `GCS`（Guarded Control Stack）支持：`s->gcs_en` 时记录返回地址，这是 QEMU 对新架构特性的扩展，不影响 C3/C6 主语义。

### 2.4 `BR/BLR/RET`：寄存器分支

**规范**：
- `BR`：PC = Xn（DDI 0487 §C3.1.3）。
- `BLR`：PC = Xn，且 `X30 = PC+4`。
- `RET`：语义上等价于跳到 Xn，但提供“return from subroutine”提示。

**QEMU 实现**：`translate-a64.c:1800-1835`

```c
trans_BR  -> gen_a64_set_pc(s, cpu_reg(s, a->rn));
trans_BLR -> gen_a64_set_pc(...) + X30 = PC+4;
trans_RET -> target = cpu_reg(s, a->rn);
             gen_a64_set_pc(...) / gen_load_check_gcs_record(...)
```

QEMU 还在 BTI/PAuth/GCS 路径上做了增强：
- `set_btype_for_br()`、`set_btype_for_blr()` 为 `BTI` 设置 `BTYPE`
- `RET` 在 `gcs_en` 下使用 `gen_load_check_gcs_record()`

**结论**：✓ 主语义符合规范；QEMU 额外叠加了 FEAT_BTI / FEAT_GCS / PAuth 扩展。

### 2.5 `B.cond / CBZ / TBZ`

**规范**：
- `B.cond` 依据 NZCV 条件码跳转（DDI 0487 §C3.1.1）。
- `CBZ/CBNZ` 比较寄存器与 0。
- `TBZ/TBNZ` 测试寄存器某一位。

**QEMU 实现**：`translate-a64.c:1720-1775`
- `trans_CBZ()`：对 `Rt` 与 0 做 `brcond`
- `trans_TBZ()`：先 `andi` 掩码，再与 0 比较
- `trans_B_cond()`：调用 `arm_gen_test_cc(a->cond, ...)`

**结论**：✓ 与规范一致。

### 2.6 分支指令编码图（简化）

```text
B / BL (DDI 0487 §C3.1.2)
31      26 25                              0
+---------+--------------------------------+
| op=00101|            imm26               |
+---------+--------------------------------+
  B:  op[31]=0
  BL: op[31]=1

BR / BLR / RET (DDI 0487 §C3.1.3)
1101011 op 11111 000000 Rn 00000
         000 = BR
         001 = BLR
         010 = RET
```

## 3. 异常生成指令验证（§C3，重点 §C3.1.5）

### 3.1 `SVC`

**规范**：`SVC` 生成 Supervisor Call 异常，EC=0x15；伪代码为 `AArch64.CheckForSVCTrap(); AArch64.CallSupervisor();`（DDI 0487 §C3.1.5、§C6.2.465）。

**QEMU**：`translate-a64.c:3155-3170`

```c
uint32_t syndrome = syn_aa64_svc(a->imm);
if (s->fgt_svc) {
    gen_exception_insn_el(s, 0, EXCP_UDEF, syndrome, 2);
    return true;
}
gen_ss_advance(s);
gen_exception_insn(s, 4, EXCP_SWI, syndrome);
```

**验证点**：
1. 先生成 syndrome，符合 ESR 记录要求。✓
2. 执行 `gen_ss_advance(s)`，符合单步调试要求。✓
3. 若 FEAT_FGT 对 `SVC` 生效，则改为 trap to EL2。✓

**结论**：✓ 与规范一致，且把 `CheckForSVCTrap()` 显式展开成 `fgt_svc` 检查。

### 3.2 `HVC`

**规范**：`HVC` 目标是 EL2，EC=0x16；在 EL0、EL2 不存在、`SCR_EL3.HCE=0` 或 `HCR_EL2.HCD=1` 等条件下为 `UNDEFINED`（DDI 0487 §C6.2.174）。

**QEMU**：
- `translate-a64.c:3173-3190`：翻译期拒绝 EL0；随后调用 `gen_helper_pre_hvc()`。
- `op_helper.c:1071-1109`：运行期检查 EL2 存在、`SCR_HCE/HCR_HCD`、PSCI 例外等。

**关键实现**：
```c
int target_el = s->current_el == 3 ? 3 : 2;
if (s->current_el == 0) unallocated_encoding(s);
gen_helper_pre_hvc(tcg_env);
gen_ss_advance(s);
gen_exception_insn_el(..., EXCP_HVC, ..., target_el);
```

**结论**：✓ 与规范一致；QEMU 把“是否 UNDEF”放到 helper 中延后判定，从而兼容 PSCI conduit 的特殊路径。

### 3.3 `SMC`

**规范**：`SMC` 目标通常是 EL3，EC=0x17；EL0 为 UNDEF；若 `HCR_EL2.TSC=1` 且 EL2 生效，则可改为 trap to EL2；若 `SCR_EL3.SMD=1`，则可能 UNDEF（DDI 0487 §C6.2.371）。

**QEMU**：
- `translate-a64.c:3193-3204`
- `op_helper.c:1111-1200`

`pre_smc()` 内部注释直接给出了规范决策表：
- `HCR_TSC` 在 NS EL1 下优先把 `SMC` 送往 EL2
- `SCR_SMD` 控制是否 UNDEF
- PSCI conduit 为 `SMC` 时可转为 QEMU 固件调用

**结论**：✓ 与规范一致，而且 helper 注释比既有文档更接近 ARM ARM 的完整判定矩阵。

### 3.4 `BRK` 与 `HLT`

**规范**：
- `BRK`：软件断点，EC=0x3c（DDI 0487 §C6.2.49）
- `HLT`：halting debug 指令；若 halting debug 未启用应 `UNDEF`（DDI 0487 §C6.2.173）

**QEMU**：
- `trans_BRK()` → `gen_exception_bkpt_insn(s, syn_aa64_bkpt(...))`
- `trans_HLT()`：除 semihosting 特例 `HLT #0xf000` 外，统一 `unallocated_encoding(s)`

**结论**：
- `BRK`：✓
- `HLT`：✓，且 QEMU 的 semihosting 是额外实现，不属于 C3/C6 本体。

### 3.5 `ERET`

**规范**：`ERET` 从 `ELR_ELx` 取返回地址，并从 `SPSR_ELx` 恢复 PSTATE；EL0 执行应 UNDEF（DDI 0487 §C3.1.5.2、§C6.2.157）。

**QEMU**：`translate-a64.c:1951-2007`

```c
if (s->current_el == 0) return false;
if (s->trap_eret) {
    gen_exception_insn_el(s, 0, EXCP_UDEF, syn_erettrap(...), 2);
}
tcg_gen_ld_i64(dst, tcg_env, offsetof(CPUARMState, elr_el[s->current_el]));
gen_helper_exception_return(tcg_env, dst);
s->base.is_jmp = DISAS_EXIT;
```

**结论**：✓
- EL0 不允许执行；
- FGT 可 trap to EL2；
- 真正的 PSTATE/SPSR 恢复在 `gen_helper_exception_return()` 完成。

### 3.6 异常类编码图（简化）

```text
SVC / HVC / SMC / BRK / HLT
11010100 opc imm16 000 op2
  opc/op2 组合区分：
  SVC = ...00001
  HVC = ...00010
  SMC = ...00011
  BRK = 001 .... 00000
  HLT = 010 .... 00000
```

## 4. 系统指令验证

### 4.1 `MRS/MSR/SYS/SYSL` 总框架

**规范**：
- `MRS`：系统寄存器读到 GPR（DDI 0487 §C6.2.286）
- `SYS/SYSL`：系统指令/带结果系统指令（DDI 0487 §C6.2.474、§C6.2.475）
- `AT/DC/IC/TLBI` 等均是 `SYS` 别名族

**QEMU**：`translate-a64.c:2764-3152` 的 `handle_sys()`

这条路径非常关键，它完成了：
1. 五元组编码 `op0/op1/crn/crm/op2` → `ARMCPRegInfo` 查找
2. 静态权限检查 `cp_access_ok()`
3. VHE / NV / NV2 重定向
4. `accessfn` / `fgt` 运行期 trap 检查
5. 特殊寄存器语义分派（`CURRENTEL`、`DC_ZVA` 等）
6. 普通寄存器读写与 TB 结束策略

**结论**：QEMU 的 `SYS` 路径并不是“按指令名硬编码”，而是“**解码后查表 + 运行时权限框架**”。这与 ARM ARM 对 system instruction 的抽象方式高度一致。✓

### 4.2 `MSR/MRS` 与系统寄存器访问

`a64.decode`：
```text
SYS  1101 0101 00 l:1 01/10/11 ...
```
其中 `l=1` 表示 read 类（`MRS/SYSL`），`l=0` 表示 write 类（`MSR/SYS`）。

`handle_sys()` 中的关键点：
- `ARM_CP_CURRENTEL`：直接返回 `current_el << 2`
- `ARM_CP_DC_ZVA`：不走普通寄存器读写，而调用 `gen_helper_dc_zva`
- 若 `write` 且非 `ARM_CP_SUPPRESS_TB_END`，默认 `need_exit_tb = true`

**规范对照结论**：✓
- 编码、访问权限、异常、结果寄存器写回都满足 ARM ARM 框架。
- QEMU 将大量“别名系统指令”统一纳入 cpreg/系统指令基础设施，而不是单独写 `trans_MSR_xxx`。

### 4.3 `DMB / DSB / ISB`

#### 4.3.1 规范要求
- `DMB`：保证内存访问观察顺序（DDI 0487 §C6.2.150）
- `DSB`：保证内存访问完成（DDI 0487 §C6.2.152）
- `ISB`：上下文同步事件，刷新取指/流水线（DDI 0487 §C6.2.177）

#### 4.3.2 QEMU 实现

`translate-a64.c:2243-2281`

```c
trans_DSB_DMB():
  Reads  -> TCG_MO_LD_LD | TCG_MO_LD_ST
  Writes -> TCG_MO_ST_ST
  All    -> TCG_MO_ALL
  tcg_gen_mb(bar)

trans_ISB():
  reset_btype(s);
  gen_goto_tb(s, 0, 4);
```

#### 4.3.3 验证结论
- **架构语义**：`DMB` 与 `DSB` 在 ARM ARM 中有区别。✓
- **QEMU 实现**：二者在 TCG 中被折叠为同一个 barrier 发射点，仅按读/写/全序区分，不建模“完成缓存/TLB维护操作”的硬件差异。✓
- `ISB` 的 QEMU 语义是**结束当前 TB 并从下一条指令重新开始翻译**，这是对“context synchronization event”的合理近似。✓

### 4.4 Cache maintenance：`DC/IC`

`helper.c:3483-3537` 清楚表明：
- `IC_IALLUIS / IC_IALLU / DC_IVAC / DC_CVAC / DC_CVAU / DC_CIVAC / ...` 多数为 `ARM_CP_NOP`
- `IC_IVAU`：
  - `CONFIG_USER_ONLY` 下 `writefn = ic_ivau_write()`，会 `tb_invalidate_phys_range()`
  - 否则 `.type = ARM_CP_NOP`
- `DC_ZVA`：特殊类型 `ARM_CP_DC_ZVA`，经 `handle_sys()` 调 `gen_helper_dc_zva`

**结论**：
- “QEMU 不模拟真实 cache”这一主结论成立。✓
- 但 `IC IVAU` 的“TB 失效”必须带上 **user-only 限定**；system-mode 下它仍然只是 `NOP + trap/permission semantics`。这一点对勘误很重要。

### 4.5 `AT` 与 `PAR_EL1`

**规范关联**：`AT` 属于 `SYS` 指令别名族；结果写入 `PAR_EL1`。既有文档主要引用系统寄存器章节，但其行为与 `SYS` 框架、异常/翻译规则紧密相关。

**QEMU**：`cpregs-at.c`
- `do_ats_write()`：执行翻译、在 fault 场景下决定“写 PAR”还是“直接抛异常”
- `ats_write64()`：根据 `AT S1E1R/S1E0W/S12E1R/S1E2R/S1E3W` 选择对应 `ARMMMUIdx`
- `v8_ats_reginfo[]`：给出完整 `opc0/opc1/crn/crm/opc2` 编码映射

**关键核验点**：
1. `PAR_EL1.SH` 对 Device / Normal-NC 强制编码为 `0b10`（`cpregs-at.c:13-24`），与伪代码 `PAREncodeShareability()` 一致。✓
2. `AT S1E0* / S1E1*` 在 EL1 下若命中 stage-2 translation-walk fault，可直接 raise Data Abort 到 EL2/EL3，而不是仅写失败 PAR（`cpregs-at.c:44-111`）。✓
3. `AT S1E2*` 与 `AT S1E3*` 的 EL 限制由 reginfo 和 accessfn 保证。✓

### 4.6 `TLBI`

`TLBI` 在规范中同样作为 `SYS` 别名族出现；QEMU 采用 cpreg 写回调处理，而不是在 `translate-a64.c` 中专门写一个 `trans_TLBI`。

**验证结论**：
- 既有文档把 TLBI 归类为“系统寄存器写入路径实现”是正确的。✓
- 从当前实现结构看，`TLBI` 的核心不是 decode 层，而是 `ARMCPRegInfo + accessfn + writefn`。✓

## 5. 数据处理指令验证（§C6）

### 5.1 `ADD/SUB`：immediate / shifted / extended

**规范**：
- `ADD (immediate)`：§C6.2.5
- `ADD (shifted register)`：§C6.2.6
- `ADD (extended register)`：§C6.2.4
- `SUB` 对应：§C6.2.455/456/457

**decode**：`a64.decode:107-121`

```text
ADD_i / ADDS_i / SUB_i / SUBS_i
@addsub_imm / @addsub_imm12
```

**实现**：
- immediate 族由对应 `trans_*_i` / 公共路径处理
- shifted register：`do_addsub_reg()`（`translate-a64.c:8934-8975`）
- extended register：`do_addsub_ext()`（`translate-a64.c:8886-8932`）

**QEMU 语义特征**：
- shifted 形式通过 `shift_reg_imm()` 处理移位
- extended 形式通过 `ext_and_shift_reg()` 处理 `UXTB/UXTH/UXTW/SXTB/...`
- `setflags` 路径调用 `gen_add_CC()/gen_sub_CC()` 更新 NZCV

**结论**：✓ 与 §C6.2 的分类和操作模型一致。

### 5.2 逻辑指令：`AND/ORR/EOR/ANDS`

**规范**：
- `AND (immediate)`：§C6.2.14
- `ANDS (shifted register)`：§C6.2.17
- `ORR (shifted register)`：§C6.2.301
- `EOR (shifted register)`：§C6.2.156

**decode**：
- immediate：`a64.decode:131-145`
- shifted register：在逻辑寄存器编码区映射到 `AND_r/ANDS_r/ORR_r/EOR_r`

**实现**：
- immediate：`logic_imm_decode_wmask()` + `gen_rri_log()`（`translate-a64.c:5093-5192`）
- register：`do_logic_reg()`（`translate-a64.c:8827-8884`）

`logic_imm_decode_wmask()` 明确对应 ARM ARM 的 `DecodeBitMasks()` 简化版：
- 无效 `immn/imms/immr` 返回 false → guest `UNDEF`
- 64/32/16/8/4/2-bit element replication 与规范一致

**结论**：✓ QEMU 对 logical immediate 的实现与 ARM 伪代码高度同构；这是一处“规范到代码”的直接映射。

### 5.3 Bitfield：`SBFM/UBFM/BFM`

**规范**：
- `SBFM`：§C6.2.354
- `UBFM`：§C6.2.486
- `BFM`：§C6.2.39

**decode**：`a64.decode:169-180`

```text
SBFM  . 00 100110 ...
BFM   . 01 100110 ...
UBFM  . 10 100110 ...
```

**实现**：`translate-a64.c:5236-5329`
- `si >= ri`：提取连续位段放到低位
- `si < ri`：执行 wrap-around 形式的 deposit
- `SBFM` 使用 `sextract`，`UBFM` 用 `extract`，`BFM` 保留目的寄存器其它位

**结论**：✓ 与规范描述完全一致。

### 5.4 `EXTR`

**规范**：`EXTR` 从寄存器对中抽取位段，且是 `ROR (immediate)` 的基础别名之一（DDI 0487 §C6.2.160）。

**QEMU**：`translate-a64.c:5331-5365`
- `imm==0` 单独特判
- 64 位用 `tcg_gen_extract2_i64`
- 32 位在 `rm==rn` 时直接退化为 `rotri_i32`

**结论**：✓ 与规范一致，且优化了 alias 场景。

### 5.5 `CSEL` / `CSINC` / `CSINV` / `CSNEG`

**规范**：`CSEL` 写真值寄存器或假值寄存器；其它几条只是 else-path 变换（DDI 0487 §C6.2.138）。

**decode**：`a64.decode:811-813`

```text
CSEL sf:1 else_inv:1 011010100 rm:5 cond:4 0 else_inc:1 rn:5 rd:5
```

这个 decode 很漂亮：`else_inv/else_inc` 两个位把 `CSEL/CSINC/CSINV/CSNEG/CSET/CSETM` 全都压进同一编码模板。

**QEMU**：`translate-a64.c:9195-9229`
- 特判 `rn==rm==31` 的 `CSET/CSETM`
- else-path 根据 `else_inv/else_inc` 做 `not/+1/neg`
- 最终统一 `tcg_gen_movcond_i64()`

**结论**：✓ 这与规范的条件选择家族结构完全一致。

## 6. 加载存储指令验证（§C6）

### 6.1 `LDR/STR`：immediate / register

**规范**：
- `LDR (immediate)`：§C6.2.215
- `STR (immediate)`：§C6.2.414
- 另有 `LDR (register)` / `STR (register)`

**QEMU**：
- immediate：`trans_LDR_i()/trans_STR_i()`（`translate-a64.c:3904-3937`）
- register offset：`trans_LDR()/trans_STR()`（`translate-a64.c:3988-4020`）
- 地址形成：
  - `op_addr_ldst_imm_pre()`：base + signed/unsigned immediate
  - `op_addr_ldst_pre()`：base + extended/shifted register

**关键点**：
- `ldst_iss_sf()` 负责同步异常 syndrome 中的 SF 位
- `gen_check_sp_alignment()` 目前是空钩子，说明 QEMU **暂未实现** AArch64 规范要求的 SP 对齐检查异常

**结论**：
- 主路径语义 ✓
- **SP alignment fault 未精确建模**：这是当前 QEMU 对规范的一个已知性能导向折衷。

### 6.2 `LDP/STP`

**规范**：
- `LDP`：§C6.2.213
- `STP`：§C6.2.413
- 地址模式有 pre-index / post-index / signed offset

**QEMU**：`translate-a64.c:3650-3775`
- `op_addr_ldstpair_pre/post()` 处理地址与回写
- `STP/LDP` 依据 `a->p/a->w` 处理 pre/post-index 与 writeback
- 在支持 LSE2 的语境下，QEMU 尽量把 pair 访问作为一个原子/半原子操作发射

**结论**：✓ 符合规范的地址模式与寄存器对读写逻辑。

### 6.3 `LDXR/STXR`：exclusive

**规范**：
- `LDXR`：加载并建立 exclusive monitor（DDI 0487 §C6.2.265）
- `STXR`：若 monitor 仍匹配则存储，`Rd=0`；否则 `Rd=1`（DDI 0487 §C6.2.449）

**QEMU**：`translate-a64.c:3230-3400, 3502-3524`
- `gen_load_exclusive()`：记录 `exclusive_addr/exclusive_val[/high]`
- `gen_store_exclusive()`：用 `atomic_cmpxchg` 比较并提交

源码中甚至直接承认：
> “This is not actually the architecturally mandated semantics ...”

并且进一步指出：
> 只记录地址而非完整范围；默认 load/store size 匹配；这是 out-of-spec 简化。

**结论**：
- 对客体常见锁实现而言，功能上 **近似正确**。✓
- 对 ARM 规范的严格 exclusive monitor 行为来说，QEMU 是**刻意简化**。△（不是 bug，而是设计折衷）

### 6.4 `CAS / LDADD / SWP`：LSE atomic

**规范**：
- `CAS, CASA, CASAL, CASL`：§C6.2.51
- `LDADD, LDADDA, LDADDAL, LDADDL`：§C6.2.179
- `SWP, SWPA, SWPAL, SWPL`：§C6.2.466

**decode**：
```text
CAS   sz:2 001000 1 - 1 rs:5 - 11111 rn:5 rt:5
LDADD .. 111 0 00 . . 1 ..... 0000 00 ..... .....
SWP   .. 111 0 00 . . 1 ..... 1000 00 ..... .....
```

**QEMU**：
- `trans_CAS()` → `gen_compare_and_swap()` → `tcg_gen_atomic_cmpxchg_i64`
- `LDADD` / `SWP` → `do_atomic_ld()` → `tcg_gen_atomic_fetch_add_i64` / `tcg_gen_atomic_xchg_i64`
- `CASP` 使用 128-bit cmpxchg 路径

**重要实现差异**：`do_atomic_ld()` 中明确写道：
> TCG atomic primitives are all full barriers. Therefore we can ignore the Acquire and Release bits of this instruction.

这意味着：
- 从**正确性上**，QEMU 保证的顺序通常不弱于规范要求。✓
- 从**精确建模上**，QEMU 没有细分 `A / L / AL / none` 的最弱序差异，而是统一提升为 full barrier。△

## 7. QEMU TCG 翻译验证：decode tree 与规范编码的映射关系

### 7.1 当前树并非旧式 `disas_*`，而是 decodetree 驱动

当前 `translate-a64.c` 中并没有用户点名的：
- `disas_uncond_b_imm`
- `disas_system`
- `disas_exc`

取而代之的是：
1. `a64.decode` 声明编码模式
2. decodetree 自动生成分发逻辑
3. `translate-a64.c` 提供 `trans_B/trans_SYS/trans_SVC/...` 具体语义发射

**因此，验证应以“编码模板 → trans_* 处理函数”来做，而不是寻找旧版 monolithic decoder。**

### 7.2 典型映射模式

| 规范类别 | `a64.decode` 模式 | `translate-a64.c` 处理 | 说明 |
|---|---|---|---|
| Unconditional branch (immediate) | `B` / `BL` | `trans_B` / `trans_BL` | 直接转 TB |
| Conditional branch | `CBZ/TBZ/B_cond` | `trans_CBZ/TBZ/B_cond` | 发射条件分支 |
| Exception generation | `SVC/HVC/SMC/BRK/HLT` | `trans_SVC/...` | syndrome + 异常注入 |
| System register/system alias | `SYS` | `trans_SYS -> handle_sys` | 查表 + accessfn |
| Barrier | `DSB_DMB/ISB` | `trans_DSB_DMB/trans_ISB` | barrier/TB 边界 |
| Bitfield | `SBFM/BFM/UBFM` | `trans_SBFM/BFM/UBFM` | extract/deposit |
| Conditional select | `CSEL` | `trans_CSEL` | `movcond` |
| Pair ldst | `LDP/STP` | `trans_LDP/STP` | pre/post-index |
| Exclusive | `LDXR/STXR` | `trans_LDXR/STXR` | software monitor |
| LSE atomics | `CAS/LDADD/SWP` | `trans_CAS` / `do_atomic_ld` | TCG atomic primitive |

### 7.3 可归纳的三个翻译模板

#### 模板 A：直接语义发射
例：`ADD/ORR/B/CBZ/LDR/STR`
- decode 出字段
- 直接生成 TCG 算术/访存/跳转

#### 模板 B：异常前置 + helper
例：`HVC/SMC/ERET`
- 翻译期做静态非法性检查
- 运行期 helper 做配置相关合法性检查
- 最后注入异常或执行 helper 主语义

#### 模板 C：系统寄存器查表
例：`MRS/MSR/DC/IC/AT/TLBI`
- 统一走 `handle_sys()`
- 由 `ARMCPRegInfo` 决定权限、trap、side effect、是否结束 TB

**结论**：QEMU 当前 AArch64 TCG 代码结构与 ARM ARM 的指令大类划分高度一致，只是把“System instructions”进一步抽象成 cpreg 框架。

## 9. 总结

本次对照验证表明：

1. **分支指令**：`B/BL/BR/BLR/RET/B.cond/CBZ/TBZ` 的 decode 与 `trans_*` 语义都与 **DDI 0487 §C3.1.1-§C3.1.4** 一致。
2. **异常生成**：`SVC/HVC/SMC/BRK/HLT/ERET` 与 **DDI 0487 §C3.1.5 及对应 §C6.2 条目** 的主语义一致；QEMU 通过 `pre_hvc/pre_smc/exception_return` helper 处理配置相关差异。
3. **系统指令**：`MRS/MSR/SYS/SYSL` 并非零散实现，而是统一挂在 `handle_sys()` 的 cpreg 框架下；这非常符合 ARM ARM 对 system instruction 的组织方式。
4. **数据处理**：`ADD/SUB`、logical immediate、bitfield、`EXTR`、`CSEL` 等基础指令在 `a64.decode` 与 `translate-a64.c` 中均能找到与 **§C6.2** 一一对应的编码/语义实现。
5. **加载存储**：`LDR/STR/LDP/STP` 主语义正确；exclusive 与 LSE atomic 也正确，但 QEMU 在内存序与 exclusive monitor 上采用“**功能正确优先**”的简化策略。
6. **既有文档**：绝大多数结论可保留；建议至少修正两点：
   - 文档 02 中 `ISB -> DISAS_NORETURN` 的错误说法
   - 文档 32 中 `IC IVAU` 的适用范围，应限定为 user-only 的 TB 失效路径

如果后续要继续扩展这份核验，下一步最值得补充的是：
- `CMP/CCMP/ADC/SBC` 与 NZCV 更新路径
- `LDAR/STLR`、`LDAPR`、`CASP/SWPP` 的 acquire/release 精度
- `TLBI` 与 `DC/IC` 的 `accessfn` trap 细分（`HCR_TTLB/TPCP/TPU/TICAB/TDZ`）
