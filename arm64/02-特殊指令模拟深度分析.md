# 第一部分：原子与独占指令

## 1. 独占监视器架构

ARM 的独占内存访问（Exclusive Access）是实现锁、CAS 等同步原语的基础。QEMU 使用 CPU 状态中的独占监视器字段来模拟：

```c
// cpu.h:704-713 — CPUARMState 中的独占监视器状态
struct CPUARMState {
    // ...
    uint64_t exclusive_addr;    // 独占地址（-1 表示无有效监视）
    uint64_t exclusive_val;     // 独占加载的值（低 64 位）
    uint64_t exclusive_high;    // 独占加载的值（高 64 位，用于 128 位）
    // ...
};
```

**独占监视器状态机**：

```
      LDXR addr         STXR addr
┌──────┐ ──→ ┌─────────┐ ──→ ┌──────────┐
│  Open │    │ Exclusive│    │ 比较&存储  │
│(无监视)│ ←── │ (监视中)  │ ←── │(结果 0/1)│
└──────┘     └─────────┘     └──────────┘
   ↑              │
   └──────────────┘
     清除条件:
     - CLREX 指令
     - 异常/中断
     - 上下文切换
     - 其他 CPU 写入监视地址
```

**监视器清除时机**（`internals.h:691-698`）：
- `CLREX` 指令显式清除
- CPU 复位（`cpu.c:569-572`）
- 异常进入（M-profile：`m_helper.c:970-973`、`m_helper.c:1908-1910`）
- 上下文切换

## 2. LDXR / STXR（独占加载/存储）

### 2.1 解码

`a64.decode:331-344` 定义独占访问指令的位模式：

```
STXR    sz:2 001000 000 rs:5 0 11111 rn:5 rt:5
LDXR    sz:2 001000 010 11111 0 11111 rn:5 rt:5
STLXR   sz:2 001000 000 rs:5 1 11111 rn:5 rt:5
LDAXR   sz:2 001000 010 11111 1 11111 rn:5 rt:5
```

### 2.2 LDXR 翻译

`trans_LDXR()`（`translate-a64.c:3502-3524`）→ `gen_load_exclusive()`（`translate-a64.c:3241`）：

```
Guest:  LDXR X0, [X1]
        ↓ [gen_load_exclusive]
TCG IR:
  1. addr = clean_addr(X1)              // 地址清理（TBI/PAC）
  2. tmp = tcg_gen_qemu_ld_i64(addr)    // 加载内存值
  3. cpu_exclusive_addr = addr           // 记录独占地址
  4. cpu_exclusive_val = tmp             // 记录独占值
  5. X0 = tmp                           // 写入目标寄存器
```

**关键点**：LDXR 并不在 TCG 层面设置硬件独占监视器，而是在 CPU 状态中记录地址和值，供后续 STXR 比较使用。

### 2.3 STXR 翻译

`trans_STXR()`（`translate-a64.c:3502-3524`）→ `gen_store_exclusive()`（`translate-a64.c:3286`）：

```
Guest:  STXR W2, X0, [X1]    // W2 = 状态（0=成功，1=失败）
        ↓ [gen_store_exclusive]
TCG IR:
  1. addr = clean_addr(X1)
  2. if (addr != cpu_exclusive_addr)
       → W2 = 1, 跳过存储         // 地址不匹配，失败
  3. old_val = cpu_exclusive_val
  4. result = tcg_gen_atomic_cmpxchg_i64(addr, old_val, new_val)
     // 原子比较交换：若内存值==old_val，则写入 new_val
  5. if (result == old_val)
       → W2 = 0                   // CAS 成功
     else
       → W2 = 1                   // CAS 失败（其他 CPU 修改了）
  6. cpu_exclusive_addr = -1       // 清除独占监视
```

**核心实现**：STXR 被翻译为 `tcg_gen_atomic_cmpxchg_i64`，这是一个原子比较交换操作，在 MTTCG 模式下保证多 vCPU 之间的原子性。

## 3. LDXP / STXP（独占对加载/存储）

`trans_LDXP()` / `trans_STXP()`（`translate-a64.c:3575-3597`）处理 128 位独占访问：

```
Guest:  LDXP X0, X1, [X2]     // 加载 128 位
        ↓
TCG IR:
  1. 加载 128 位值到 exclusive_val:exclusive_high
  2. 记录 exclusive_addr

Guest:  STXP W3, X0, X1, [X2]  // 存储 128 位
        ↓
TCG IR:
  1. tcg_gen_atomic_cmpxchg_i128(addr, old_128, new_128)
  2. 比较结果设置状态寄存器
```

`gen_compare_and_swap_pair()`（`translate-a64.c:3420-3478`）处理 64 位对的比较交换。

## 4. LSE 原子操作（CAS / SWP / LDADD 等）

ARMv8.1 引入的 LSE（Large System Extensions）提供了直接的原子操作指令，无需独占加载/存储循环。

### 4.1 解码

`a64.decode:536-556` 定义 LSE 原子指令模式。

### 4.2 翻译

`do_atomic_ld()`（`translate-a64.c:4062-4103`）是 LSE 原子操作的通用翻译函数：

```c
static void do_atomic_ld(DisasContext *s, arg_atomic *a,
                         AtomicThreeOpFn *fn, int sign) {
    // 1. 计算清理后的地址
    // 2. 设置 MemOp（大小 + acquire/release 标志）
    // 3. 调用 TCG 原子操作函数
    fn(cpu_reg(s, a->rt), addr, cpu_reg(s, a->rs), mmu_idx, memop);
    // 4. 返回旧值到 rt
}
```

### 4.3 指令映射

| ARM64 指令 | TCG 原子操作 | 位置 |
|-----------|-------------|------|
| `CAS` | `tcg_gen_atomic_cmpxchg_i64` | `translate-a64.c:3612-3618` |
| `CASP` | `tcg_gen_atomic_cmpxchg_i128` | `translate-a64.c:3599-3609` |
| `SWP` | `tcg_gen_atomic_xchg_i64` | `translate-a64.c:4105-4113` |
| `LDADD` | `tcg_gen_atomic_fetch_add_i64` | `translate-a64.c:4105` |
| `LDCLR` | `tcg_gen_atomic_fetch_and_i64`（取反） | `translate-a64.c:4106` |
| `LDEOR` | `tcg_gen_atomic_fetch_xor_i64` | `translate-a64.c:4107` |
| `LDSET` | `tcg_gen_atomic_fetch_or_i64` | `translate-a64.c:4108` |
| `LDSMAX` | `tcg_gen_atomic_fetch_smax_i64` | `translate-a64.c:4109` |
| `LDSMIN` | `tcg_gen_atomic_fetch_smin_i64` | `translate-a64.c:4110` |
| `LDUMAX` | `tcg_gen_atomic_fetch_umax_i64` | `translate-a64.c:4111` |
| `LDUMIN` | `tcg_gen_atomic_fetch_umin_i64` | `translate-a64.c:4112` |

所有 LSE 原子操作通过 `TRANS_FEAT()` 宏注册，仅在 CPU 具有 `FEAT_LSE` 特性时可用。

### 4.4 LSE vs 独占访问的区别

```
独占访问（LDXR/STXR）:
  → 翻译为 cmpxchg + 独占监视器状态机
  → 循环重试由客户机代码实现
  → 旧代码兼容性好

LSE 原子（CAS/SWP/LDADD）:
  → 直接翻译为 TCG 原子操作
  → 单条指令完成，无需循环
  → 更高效，尤其在 MTTCG 模式下
```

## 5. Acquire / Release 语义

ARM64 的内存序语义通过指令后缀编码：

| 后缀 | 含义 | 示例 |
|------|------|------|
| 无 | Relaxed | `LDXR`, `STXR` |
| A | Acquire | `LDAXR`, `LDAR` |
| L | Release | `STLXR`, `STLR` |
| AL | Acquire + Release | `CASAL`, `SWPAL` |

### 5.1 LDAR / STLR（普通 Acquire / Release）

**STLR** 翻译（`translate-a64.c:3526-3549`）：
```
Guest:  STLR X0, [X1]    // Store-Release
        ↓
TCG IR:
  1. tcg_gen_mb(TCG_MO_ALL | TCG_BAR_STRL)   // Release 屏障
  2. tcg_gen_qemu_st_i64(val, addr, memop)    // 普通存储
```

**LDAR** 翻译（`translate-a64.c:3552-3571`）：
```
Guest:  LDAR X0, [X1]    // Load-Acquire
        ↓
TCG IR:
  1. tcg_gen_qemu_ld_i64(ret, addr, memop)    // 普通加载
  2. tcg_gen_mb(TCG_MO_ALL | TCG_BAR_LDAQ)    // Acquire 屏障
```

### 5.2 LSE 原子的 Acquire/Release

LSE 原子操作通过 `MemOp` 标志传递排序语义（`translate-a64.c:4079-4083, 4144-4147`）：

```c
// do_atomic_ld() 中的排序处理
if (acquire) memop |= MO_ACQUIRE;   // Acquire 语义
if (release) memop |= MO_RELEASE;   // Release 语义
// TCG 原子操作本身在 MTTCG 模式下作为完整屏障
```

### 5.3 TCG 屏障类型

`tcg-mo.h:28-46` 定义内存序常量：

```c
typedef enum {
    TCG_MO_LD_LD = 0x01,   // Load→Load 序
    TCG_MO_ST_LD = 0x02,   // Store→Load 序
    TCG_MO_LD_ST = 0x04,   // Load→Store 序
    TCG_MO_ST_ST = 0x08,   // Store→Store 序
    TCG_MO_ALL   = 0x0F,   // 全序

    TCG_BAR_SC   = 0x10,   // 顺序一致性屏障
    TCG_BAR_LDAQ = 0x20,   // Load-Acquire 屏障
    TCG_BAR_STRL = 0x40,   // Store-Release 屏障
} TCGBar;
```

## 6. MTTCG 原子指令处理

在多线程 TCG（MTTCG）模式下，原子指令需要特殊处理以保证跨 vCPU 的原子性。

### 6.1 EXCP_ATOMIC 异常路径

当 TCG 后端无法直接生成原子操作时（例如缺少 128 位 CAS 支持），会触发 `EXCP_ATOMIC` 异常：

```
vCPU 线程执行生成代码
  → 遇到无法内联的原子操作
  → cpu_loop_exit_atomic()                    [cputlb.c]
  → 异常码 = EXCP_ATOMIC

MTTCG 主循环处理:                             [tcg-accel-ops-mttcg.c:106-109]
  if (exception == EXCP_ATOMIC) {
      cpu_exec_step_atomic(cpu);              // 序列化执行
  }
```

### 6.2 序列化执行

`cpu_exec_step_atomic()`（`cpu-exec.c:549-598`）：

```c
int cpu_exec_step_atomic(CPUState *cpu) {
    // 1. 获取独占锁（序列化所有 vCPU）
    start_exclusive();

    // 2. 创建单指令 TB（禁用直接跳转）
    cflags = CF_NO_GOTO_TB | CF_NO_GOTO_PTR | CF_PARALLEL;
    // CF_PARALLEL 被清除 → 使用非并行模式翻译
    // 此时 cmpxchg 可以用普通 load+compare+store 实现

    // 3. 执行单条指令
    tb = tb_gen_code(cpu, pc, ..., cflags & ~CF_PARALLEL);
    cpu_tb_exec(cpu, tb);

    // 4. 释放独占锁
    end_exclusive();
}
```

**为什么需要序列化**：
- 128 位 CAS 在某些宿主平台上没有对应的原子指令
- 序列化保证在执行该指令期间没有其他 vCPU 并发访问内存
- 性能代价高，但这些指令在实际工作负载中频率较低

### 6.3 并行 vs 非并行翻译

| 模式 | CF_PARALLEL | 原子操作实现 |
|------|-------------|-------------|
| 单 CPU | 清除 | 普通 load/compare/store（无需原子） |
| MTTCG 正常 | 设置 | `tcg_gen_atomic_*`（宿主原子指令） |
| MTTCG 回退 | 清除 | 独占模式下普通操作（已序列化） |

# 第二部分：内存屏障指令

## 7. DMB / DSB（数据内存/同步屏障）

### 7.1 翻译

DMB 和 DSB 共用同一个翻译函数 `trans_DSB_DMB()`（`translate-a64.c:2243-2260`）：

```c
static bool trans_DSB_DMB(DisasContext *s, arg_DSB_DMB *a) {
    TCGBar bar;

    switch (a->types) {
    case MBReqTypes_Reads:    // LD 屏障
        bar = TCG_BAR_SC | TCG_MO_LD_LD | TCG_MO_LD_ST;
        break;
    case MBReqTypes_Writes:   // ST 屏障
        bar = TCG_BAR_SC | TCG_MO_ST_ST;
        break;
    default:                  // Full 屏障 (SY)
        bar = TCG_BAR_SC | TCG_MO_ALL;
        break;
    }
    tcg_gen_mb(bar);
    return true;
}
```

### 7.2 屏障域

ARM 定义了四种共享域，但 QEMU TCG 不区分：

| 域 | 编码 | QEMU 处理 |
|-----|------|-----------|
| NSH（Non-shareable） | 0b00 | 同等处理 |
| ISH（Inner Shareable） | 0b01 | 同等处理 |
| OSH（Outer Shareable） | 0b10 | 同等处理 |
| SY（Full System） | 0b11 | 同等处理 |

**原因**：TCG 模拟的内存模型中，所有 vCPU 共享同一地址空间，不需要区分共享域。屏障仅影响 TCG 的指令重排优化。

### 7.3 DMB vs DSB 的区别

在真实硬件上：
- **DMB**：仅保证数据内存访问的顺序
- **DSB**：保证数据访问顺序 + 等待所有缓存/TLB 维护操作完成

在 QEMU TCG 中，两者翻译为相同的 `tcg_gen_mb()`，因为 TCG 不模拟缓存一致性协议。

## 8. ISB（指令同步屏障）

`trans_ISB()`（`translate-a64.c:2272-2281`）：

```c
static bool trans_ISB(DisasContext *s, arg_ISB *a) {
    reset_btype(s);
    // ISB 强制结束当前翻译块
    gen_goto_tb(s, 0, 4);   // 跳转到下一条指令，但强制创建新 TB
    s->base.is_jmp = DISAS_NORETURN;
    return true;
}
```

**ISB 的关键效果**：
1. **结束当前 TB** — 确保 ISB 之后的指令在新的 TB 中翻译
2. **刷新流水线** — 在 TCG 中表现为强制重新查找 TB
3. **上下文同步** — 确保之前的系统寄存器修改对后续指令可见

**典型使用场景**：
```asm
MSR  SCTLR_EL1, X0    ; 修改系统控制寄存器
ISB                     ; 确保修改生效
; ... 后续指令在新配置下执行 ...
```

## 9. TCG 内存序模型

### 9.1 tcg_gen_mb() 实现

`tcg_gen_mb()`（`tcg-op.c:289-305`）：

```c
void tcg_gen_mb(TCGBar mb_type) {
    // 仅在并行模式下发射屏障
    if (tcg_ctx->gen_tb->cflags & CF_PARALLEL) {
        tcg_emit_op(INDEX_op_mb, mb_type);
    }
}
```

**重要**：在单 vCPU 模式下，`tcg_gen_mb()` 不生成任何代码（NOP），因为没有并发访问。

### 9.2 后端处理

AArch64 后端将 `INDEX_op_mb` 翻译为宿主屏障指令：
- `TCG_MO_ALL` → `DMB SY`（AArch64 宿主上）
- 部分序 → 对应的部分屏障

### 10.1 DC ZVA（零化缓存行）

`DC ZVA` 是唯一有实际实现的数据缓存操作，因为它具有可观察的内存副作用：

翻译（`translate-a64.c:2996-3012`）：
```c
// 发射 helper 调用
gen_helper_dc_zva(tcg_env, addr);
```

Helper 实现（`helper-a64.c:788-820`）：
```c
void HELPER(dc_zva)(CPUARMState *env, uint64_t addr) {
    int blocklen = 4 << env_archcpu(env)->dcz_blocksize;
    uint64_t start = addr & ~(blocklen - 1);

    // 将整个缓存行大小的内存区域清零
    for (i = 0; i < blocklen; i += 8) {
        cpu_stq_data(env, start + i, 0);
    }
}
```

### 11.1 IC IVAU（按虚拟地址失效指令缓存）

在用户模式下，`IC IVAU` 触发翻译块失效（`helper.c:3414-3441`）：

```c
static void ic_ivau_write(CPUARMState *env, ..., uint64_t value) {
    // 计算缓存行范围
    uint64_t icache_line_mask = (4 << cache_info) - 1;
    uint64_t start = value & ~icache_line_mask;
    uint64_t end = start + icache_line_mask + 1;

    // 失效该范围内的所有翻译块
    tb_invalidate_phys_range(start, end);
}
```

这对于 JIT 编译器（如 Java HotSpot）在修改代码后刷新指令缓存至关重要。

## 12. TLBI（TLB 无效化）

TLBI 指令通过系统寄存器写入路径实现，定义在 `tlb-insns.c`（1,323 行）。

### 12.1 TLBI 指令分类

AT 指令执行软件地址翻译，结果写入 `PAR_EL1` 寄存器。

### 13.1 支持的 AT 指令

`cpregs-at.c:389-490` 定义了所有 AT 指令变体：

| 指令 | 翻译阶段 | 说明 |
|------|----------|------|
| `AT S1E1R/W` | Stage 1, EL1 | 读/写翻译 |
| `AT S1E0R/W` | Stage 1, EL0 | 用户态翻译 |
| `AT S12E1R/W` | Stage 1+2, EL1 | 完整两阶段翻译 |
| `AT S12E0R/W` | Stage 1+2, EL0 | 用户态两阶段翻译 |
| `AT S1E2R/W` | Stage 1, EL2 | Hypervisor 翻译 |
| `AT S1E3R/W` | Stage 1, EL3 | 安全监视器翻译 |

### 13.2 实现

`do_ats_write()`（`cpregs-at.c:26-190`）：

```c
static void do_ats_write(CPUARMState *env, ..., uint64_t value) {
    // 1. 调用 get_phys_addr_for_at() 执行页表遍历
    bool ret = get_phys_addr_for_at(env, value, access_type, ...);

    if (ret) {
        // 翻译成功 → 构建 PAR_EL1 成功格式
        par64 = phys_addr & PAR_PA_MASK;
        par64 |= (attrs.shareability << PAR_SH_SHIFT);
        par64 |= (attrs.type << PAR_ATTR_SHIFT);
    } else {
        // 翻译失败 → 构建 PAR_EL1 错误格式
        par64 = 1;  // F 位 = 1 表示失败
        par64 |= (fsr << PAR_FST_SHIFT);  // 故障状态码
    }

    env->cp15.par_el[1] = par64;
}
```

### 13.3 PAR_EL1 结果格式

```
成功时（bit[0]=0）:
  [63:56] ATTR — 内存属性（从 MAIR 查找）
  [9:8]   SH   — 共享性
  [47:12] PA   — 物理地址
  [0]     F=0  — 成功

失败时（bit[0]=1）:
  [15:9]  FST  — 故障状态码
  [8]     EA   — 外部中止
  [6:1]   Reserved
  [0]     F=1  — 失败
```

## 15. AArch64 LPAE 页表遍历算法

`get_phys_addr_lpae()`（`ptw.c:1859-2449`）实现完整的 LPAE 页表遍历：

### 15.1 遍历流程

```
输入: VA（虚拟地址）, 翻译体制, 访问类型

1. 参数提取                            [ptw.c:1865-1973]
   ├── 从 TCR 获取: T0SZ/T1SZ, TG0/TG1, IPS
   ├── 根据 VA 最高位选择 TTBR0 或 TTBR1
   └── 确定起始级别和页表基址

2. VA→TTBR 选择                        [ptw.c:1647-1713]
   if VA[63] == 0 → 使用 TTBR0 (低地址空间)
   if VA[63] == 1 → 使用 TTBR1 (高地址空间, 内核)

3. 起始级别计算                         [ptw.c:1987-2009]
   inputsize = 64 - T0SZ (或 T1SZ)
   stride = granule_bits - 3    // 每级索引位数
   level = 4 - ceil((inputsize - page_bits) / stride)
   // 4KB 粒度: L0→L1→L2→L3
   // 64KB 粒度: L1→L2→L3

4. 页表遍历循环                         [ptw.c:2088-2141]
   while (level < 4) {
       index = (VA >> level_shift) & index_mask
       desc_addr = table_base + index * 8
       desc = 读取描述符(desc_addr)        // 从客户机物理内存加载

       if (desc == fault) → 翻译故障
       if (desc == block) → 找到块映射，跳出
       if (desc == table) → table_base = desc & ADDR_MASK
                            level++
   }

5. 描述符解析                            [ptw.c:2128-2141]
   ├── 提取物理地址 (PA)
   ├── 提取属性位 (AP, UXN, PXN, SH, AttrIndx)
   └── 计算最终物理地址 = PA + (VA & offset_mask)

6. 访问标志检查                          [ptw.c:2143-2163]
   if (!AF) → 可能触发 Access Flag 故障
             → 或硬件管理 AF（写回描述符）

7. 脏位处理                              [ptw.c:2165-2179]
   if (write && DBM && !dirty)
       → 设置脏位（如果硬件 DBM 启用）

8. 权限检查                              [ptw.c:2287-2332]
   get_S1prot()                          [ptw.c:1434-1541]
   ├── AP[2:1] → 读/写权限
   ├── UXN/PXN → 执行权限
   ├── WXN (SCTLR) → 可写即不可执行
   └── EL0/EL1 权限分离
```

### 15.2 页粒度与级数

| 粒度 | 页大小 | 级数 | 每级索引位 | 最大 VA 位数 |
|------|--------|------|-----------|-------------|
| 4 KB | 4 KiB | L0-L3 | 9 | 48 (或 52) |
| 16 KB | 16 KiB | L0-L3 | 11 | 48 (或 52) |
| 64 KB | 64 KiB | L1-L3 | 13 | 48 (或 52) |

### 15.3 描述符格式

```
64 位描述符:

Invalid:   [1:0] = 0b00
Block:     [1:0] = 0b01   (L0/L1/L2 — 映射大块连续物理内存)
Table:     [1:0] = 0b11   (L0/L1/L2 — 指向下一级页表)
Page:      [1:0] = 0b11   (L3 — 最终页映射)

Block/Page 描述符属性位:
  [54]    UXN/XN    — 用户态不可执行
  [53]    PXN       — 特权态不可执行
  [52]    Contiguous — 连续映射提示
  [51]    DBM       — 脏位管理
  [11:10] AF        — 访问标志
  [9:8]   SH        — 共享性
  [7:6]   AP[2:1]   — 访问权限
  [4:2]   AttrIndx  — MAIR 属性索引
```

## 19. Stage 2 虚拟化翻译

### 19.1 两阶段翻译

### 21.1 MAIR_EL1

`MAIR_EL1`（`helper.c:990-998`）定义 8 个内存属性槽位，每个 8 位：

```
MAIR_EL1 = [Attr7][Attr6][Attr5][Attr4][Attr3][Attr2][Attr1][Attr0]
             63:56  55:48  47:40  39:32  31:24  23:16  15:8   7:0

每个 AttrN 编码:
  0b0000_0000  — Device-nGnRnE（最严格的设备内存）
  0b0000_0100  — Device-nGnRE
  0b0000_1000  — Device-nGRE
  0b0000_1100  — Device-GRE
  0b0100_0100  — Normal, Outer Non-cacheable, Inner Non-cacheable
```

```c
// combined_attrs_nofwb() — 非 FWB 模式
// 规则: 取更弱的缓存属性
// Device > Non-cacheable > Write-Through > Write-Back
// 即: S1=WB + S2=NC → 结果=NC

// combined_attrs_fwb() — FWB (Force Write-Back) 模式
// Stage 2 可强制覆盖 Stage 1 属性
```

### 21.4 QEMU 对内存类型的处理

| 类型 | QEMU 行为 |
|------|-----------|
| Normal, Write-Back | 直接宿主内存访问（最快） |
| Normal, Non-cacheable | 同上（QEMU 不模拟缓存） |
| Device-nGnRnE | 标记为设备内存，可能触发 MMIO 分发 |
| Device-nGnRE | 同上 |

**关键区别**：Device 内存不允许推测访问，QEMU 通过 `TLB_FILL_FLAG_DEVICE` 标志在 TLB 条目中标记。
