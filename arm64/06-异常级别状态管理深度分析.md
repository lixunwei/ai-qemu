## 1. 概述

ARM64（AArch64）架构定义了四个异常级别（Exception Level, EL）：

| 异常级别 | 用途 | 典型运行软件 |
|---------|------|------------|
| EL0 | 用户态（非特权） | 应用程序 |
| EL1 | 内核态（特权） | 操作系统内核 |
| EL2 | Hypervisor 态 | 虚拟机监控器 |
| EL3 | Secure Monitor 态 | 安全固件（如 TF-A） |

在 QEMU 中，EL 状态管理是 ARM64 模拟的核心机制之一。每次 EL 切换都涉及：
- PSTATE 的保存/恢复
- SP 栈指针的切换（banking）
- 向量表地址计算
- MMU 模式切换
- hflags（翻译块标志）重建
- SVE/SME 向量长度调整
- 中断屏蔽位更新

本文深入分析 QEMU 如何在软件层面精确模拟这些硬件行为。

## 2. 异常级别基本概念

### 2.1 AArch64 PSTATE Mode 编码

QEMU 定义 AArch64 PSTATE 模式常量（`cpu.h:1574-1581`）：

```c
#define PSTATE_MODE_EL0t  0   // EL0, 使用 SP_EL0
#define PSTATE_MODE_EL1t  4   // EL1, 使用 SP_EL0
#define PSTATE_MODE_EL1h  5   // EL1, 使用 SP_EL1
#define PSTATE_MODE_EL2t  8   // EL2, 使用 SP_EL0
#define PSTATE_MODE_EL2h  9   // EL2, 使用 SP_EL2
#define PSTATE_MODE_EL3t  12  // EL3, 使用 SP_EL0
#define PSTATE_MODE_EL3h  13  // EL3, 使用 SP_EL3
```

模式编码规则：
- **Bit[3:2]** = 异常级别（0/1/2/3）
- **Bit[0]** = SP 选择（0=SP_EL0, 1=SP_ELx）——即 `PSTATE.SP` 位
- **Bit[1]** = 保留（必须为 0）

### 2.2 EL 宽度决定

每个 EL 可以独立配置运行 AArch64 或 AArch32。`arm_el_is_aa64()` 是判定函数（`internals.h:452-483`）：

```c
static inline bool arm_el_is_aa64(CPUARMState *env, int el)
{
    assert(el >= 1 && el <= 3);
    bool aa64 = arm_feature(env, ARM_FEATURE_AARCH64);

    if (el == 3) {
        return aa64;  // EL3 始终使用 CPU 最高支持宽度
    }
    if (arm_feature(env, ARM_FEATURE_EL3)) {
        aa64 = aa64 && arm_scr_rw_eff(env);  // SCR_EL3.RW 控制 EL2 宽度
    }
    if (el == 2) {
        return aa64;
    }
    if (arm_is_el2_enabled(env)) {
        aa64 = aa64 && (env->cp15.hcr_el2 & HCR_RW);  // HCR_EL2.RW 控制 EL1 宽度
    }
    return aa64;
}
```

**层级控制链：**
```
EL3 宽度 ← ARM_FEATURE_AARCH64（CPU 硬件特性）
EL2 宽度 ← SCR_EL3.RW（EL3 控制）
EL1 宽度 ← HCR_EL2.RW（EL2 控制）
EL0 宽度 ← 当前运行时状态（is_a64(env)）
```

## 3. PSTATE 与当前 EL 追踪

### 3.1 PSTATE 存储结构

QEMU 将 PSTATE 的各字段分散存储在 `CPUARMState` 中以提升访问效率（`cpu.h:270-315`）：

```c
uint64_t pstate;     // 主要 PSTATE 位（EL、SP 等）
bool     aarch64;    // PSTATE.nRW 的反转 —— true 表示 AArch64
uint32_t CF;         // 进位标志，独立存储
uint32_t VF;         // 溢出标志
uint32_t NF;         // 负标志
uint32_t ZF;         // 零标志
uint64_t daif;       // DAIF 异常屏蔽位，独立存储
uint32_t btype;      // BTI 分支类型
uint64_t svcr;       // PSTATE.{SM,ZA} 位（SME 相关）
```

**关键设计决策：** NZCV 标志和 DAIF 异常屏蔽位从 `pstate` 中分离出来独立存储，因为它们是最频繁访问的状态位。翻译时通过 `pstate_read()` / `pstate_write()` 组装完整 PSTATE。

### 3.2 当前 EL 获取

`arm_current_el()` 是获取当前异常级别的核心函数（`internals.h:489-515`）：

```c
static inline int arm_current_el(CPUARMState *env)
{
    if (arm_feature(env, ARM_FEATURE_M)) {
        return arm_v7m_is_handler_mode(env) || ...;  // M-Profile 特殊处理
    }
    if (is_a64(env)) {
        return extract32(env->pstate, 2, 2);  // AArch64：直接从 PSTATE[3:2] 提取
    }
    // AArch32：从 CPSR 的 Mode 字段推导
    switch (env->uncached_cpsr & 0x1f) {
    case ARM_CPU_MODE_USR:  return 0;
    case ARM_CPU_MODE_HYP:  return 2;
    case ARM_CPU_MODE_MON:  return 3;
    default:
        if (arm_is_secure(env) && !arm_el_is_aa64(env, 3)) {
            return 3;  // AArch32 Secure 特权模式 → EL3
        }
        return 1;  // SVC/FIQ/IRQ/ABT/UND/SYS → EL1
    }
}
```

**AArch64 vs AArch32 差异：**
- AArch64：EL 直接编码在 PSTATE 中，两个比特位
- AArch32：EL 需从 CPSR Mode 字段（5 位）间接推导

## 4. EL 相关的寄存器 Banking

### 4.1 Banking 寄存器组

每个 EL 拥有独立的关键寄存器组（`cpu.h:296-318`）：

```c
uint64_t elr_el[4];        // ELR_EL1/EL2/EL3（异常链接寄存器）
uint64_t sp_el[4];         // SP_EL0/EL1/EL2/EL3（栈指针）
uint64_t banked_spsr[8];   // SPSR_EL1/EL2/EL3 等（保存的程序状态）
```

### 4.2 SP 保存与恢复

`aarch64_save_sp()` 和 `aarch64_restore_sp()` 负责 SP banking（`internals.h:565-581`）：

```c
static inline void aarch64_save_sp(CPUARMState *env, int el)
{
    if (env->pstate & PSTATE_SP) {
        env->sp_el[el] = env->xregs[31];   // 当前使用 SP_ELx → 保存到 sp_el[el]
    } else {
        env->sp_el[0] = env->xregs[31];    // 当前使用 SP_EL0 → 保存到 sp_el[0]
    }
}

static inline void aarch64_restore_sp(CPUARMState *env, int el)
{
    if (env->pstate & PSTATE_SP) {
        env->xregs[31] = env->sp_el[el];   // 加载 SP_ELx
    } else {
        env->xregs[31] = env->sp_el[0];    // 加载 SP_EL0
    }
}
```

### 4.3 SPSel 切换

`update_spsel()` 实现 MSR SPSel 指令的行为（`internals.h:583-600`）：

```c
static inline void update_spsel(CPUARMState *env, uint32_t imm)
{
    unsigned int cur_el = arm_current_el(env);
    if (!((imm ^ env->pstate) & PSTATE_SP)) {
        return;  // SP 选择未改变，无需操作
    }
    aarch64_save_sp(env, cur_el);            // 保存当前 SP
    env->pstate = deposit32(env->pstate, 0, 1, imm);  // 更新 PSTATE.SP
    assert(cur_el >= 1 && cur_el <= 3);      // EL0 不允许 SPSel
    aarch64_restore_sp(env, cur_el);         // 加载新 SP
}
```

## 5. 异常进入流程（EL 上升）

### 5.1 主入口函数

`arm_cpu_do_interrupt_aarch64()` 是 AArch64 异常进入的核心函数（`helper.c:9198-9428`）。完整流程分为以下步骤：

### 5.2 第一步：确定目标 EL 和向量偏移

```c
unsigned int new_el = env->exception.target_el;   // 目标 EL（由异常路由逻辑预设）
vaddr addr = env->cp15.vbar_el[new_el];           // 向量表基地址
```

**向量偏移计算（来自低 EL 的异常）：**

| 条件 | 偏移 | 说明 |
|------|------|------|
| cur_el < new_el，低 EL 运行 AArch64 | +0x400 | 从低 EL（AArch64）进入 |
| cur_el < new_el，低 EL 运行 AArch32 | +0x600 | 从低 EL（AArch32）进入 |
| cur_el == new_el，使用 SP_ELx | +0x200 | 同 EL，当前使用 SP_ELx |
| cur_el == new_el，使用 SP_EL0 | +0x000 | 同 EL，当前使用 SP_EL0 |

**按异常类型的额外偏移：**

| 异常类型 | 额外偏移 |
|---------|---------|
| Synchronous（SVC/数据中止等） | +0x00 |
| IRQ | +0x80 |
| FIQ | +0x100 |
| SError | +0x180 |

源码（`helper.c:9217-9338`）：

```c
if (cur_el < new_el) {
    // 判断低 EL 的执行状态
    bool is_aa64;
    switch (new_el) {
    case 3: is_aa64 = arm_scr_rw_eff(env); break;
    case 2: /* 通过 HCR_EL2 判断 */ ... break;
    case 1: is_aa64 = is_a64(env); break;
    }
    addr += is_aa64 ? 0x400 : 0x600;
} else {
    if (pstate_read(env) & PSTATE_SP) addr += 0x200;
}
// 再加异常类型偏移
switch (cs->exception_index) {
case EXCP_IRQ: case EXCP_VIRQ: addr += 0x80; break;
case EXCP_FIQ: case EXCP_VFIQ: addr += 0x100; break;
case EXCP_VSERR:               addr += 0x180; break;
// Synchronous: 无额外偏移
}
```

### 5.3 第二步：保存旧状态

```c
// 保存 PSTATE → SPSR_ELx
if (is_a64(env)) {
    old_mode = pstate_read(env);            // 组装完整 PSTATE
    aarch64_save_sp(env, arm_current_el(env));  // 保存当前 SP
    env->elr_el[new_el] = env->pc;         // PC → ELR_ELx
} else {
    old_mode = cpsr_read_for_spsr_elx(env); // AArch32: CPSR → SPSR
    env->elr_el[new_el] = env->regs[15];   // R15(PC) → ELR_ELx
    aarch64_sync_32_to_64(env);            // 同步 32 位寄存器到 64 位视图
}
env->banked_spsr[aarch64_banked_spsr_index(new_el)] = old_mode;
```

### 5.4 第三步：构造新 PSTATE

```c
uint64_t new_mode = aarch64_pstate_mode(new_el, true);  // 基础模式 = ELxh
// 处理 PAN
if (cpu_isar_feature(aa64_pan, cpu)) {
    new_mode |= old_mode & PSTATE_PAN;        // 默认继承旧 PAN
    if ((new_el == 1 || VHE_EL2) && !(sctlr & SCTLR_SPAN)) {
        new_mode |= PSTATE_PAN;               // SPAN=0 时强制设置 PAN=1
    }
}
// MTE: 设置 TCO（Tag Check Override）
if (cpu_isar_feature(aa64_mte, cpu)) {
    new_mode |= PSTATE_TCO;
}
// SSBS: 从 SCTLR_ELx.DSSBS 初始化
if (cpu_isar_feature(aa64_ssbs, cpu)) {
    new_mode = (sctlr & SCTLR_DSSBS_64) ? (new_mode | PSTATE_SSBS)
                                          : (new_mode & ~PSTATE_SSBS);
}
// NMI: ALLINT 从 SCTLR.SPINTMASK 初始化
if (cpu_isar_feature(aa64_nmi, cpu)) {
    new_mode = (sctlr & SCTLR_SPINTMASK) ? (new_mode & ~PSTATE_ALLINT)
                                           : (new_mode | PSTATE_ALLINT);
}
// 写入 PSTATE，DAIF 全部屏蔽
pstate_write(env, PSTATE_DAIF | new_mode);
env->aarch64 = true;
```

### 5.5 第四步：恢复目标 EL 的 SP 并完成

```c
aarch64_restore_sp(env, new_el);    // 加载 SP_ELx（因为 new_mode 是 ELxh）
arm_rebuild_hflags(env);            // 重建翻译块标志
env->pc = addr;                     // 设置新 PC = VBAR + offset
```

## 6. 异常返回流程（ERET，EL 下降）

### 6.1 主入口

`HELPER(exception_return)()` 处理 ERET 指令（`helper-a64.c:622-785`）。

### 6.2 完整流程

**Step 1：读取 SPSR 并保存当前 SP**
```c
int cur_el = arm_current_el(env);
uint64_t spsr = env->banked_spsr[aarch64_banked_spsr_index(cur_el)];
aarch64_save_sp(env, cur_el);
arm_clear_exclusive(env);  // 清除独占监控器
```

**Step 2：确定目标 EL**

`el_from_spsr()` 从 SPSR 解析目标 EL（`helper-a64.c:584-620`）：

```c
static int el_from_spsr(uint32_t spsr)
{
    if (spsr & PSTATE_nRW) {
        // AArch32 返回
        switch (spsr & CPSR_M) {
        case ARM_CPU_MODE_USR: return 0;
        case ARM_CPU_MODE_HYP: return 2;
        case ARM_CPU_MODE_FIQ/IRQ/SVC/ABT/UND/SYS: return 1;
        case ARM_CPU_MODE_MON: return -1;  // 非法
        }
    } else {
        // AArch64 返回
        if (extract32(spsr, 1, 1)) return -1;  // M[1] 保留位非零
        if (extract32(spsr, 0, 4) == 1) return -1;  // EL0h 非法
        return extract32(spsr, 2, 2);  // 从 M[3:2] 获取 EL
    }
}
```

**Step 3：合法性检查**（`helper-a64.c:646-691`）

| 检查条件 | 结果 |
|---------|------|
| 目标 EL > 当前 EL | 非法返回 |
| 目标 EL2 但 EL2 未启用 | 非法返回 |
| EL3 安全状态限制（FEAT_RME） | 非法返回 |
| 目标 EL 宽度与 SPSR.nRW 不匹配 | 非法返回 |
| 返回 AArch32 但 CPU 仅支持 AArch64 | 非法返回 |
| 返回 EL1 但 HCR_EL2.TGE=1 | 非法返回 |
| GCS EXLOCK 检查 | 非法返回 |

**Step 4a：返回到 AArch64**（`helper-a64.c:718-752`）
```c
env->aarch64 = true;
spsr &= aarch64_pstate_valid_mask(&cpu->isar);  // 屏蔽无效位
pstate_write(env, spsr);                         // SPSR → PSTATE
aarch64_restore_sp(env, new_el);                 // 加载目标 EL 的 SP
helper_rebuild_hflags_a64(env, new_el);          // 重建 hflags
// TBI 处理后设置 PC
env->pc = new_pc;
```

**Step 4b：返回到 AArch32**（`helper-a64.c:697-717`）
```c
env->aarch64 = false;
cpsr_write_from_spsr_elx(env, spsr);   // SPSR → CPSR
aarch64_sync_64_to_32(env);            // 64 位寄存器同步到 32 位视图
env->regs[15] = new_pc;               // 设置 PC（对齐处理）
helper_rebuild_hflags_a32(env, new_el);
```

## 7. SVC/HVC/SMC 异常路由

### 7.1 SVC（Supervisor Call：EL0→EL1）

翻译阶段处理（`translate-a64.c:3155-3171`）：

```c
static bool trans_SVC(DisasContext *s, arg_i *a)
{
    uint32_t syndrome = syn_aa64_svc(a->imm);
    if (s->fgt_svc) {
        // 细粒度陷阱：SVC 被路由到 EL2
        gen_exception_insn_el(s, 0, EXCP_UDEF, syndrome, 2);
        return true;
    }
    gen_ss_advance(s);
    gen_exception_insn(s, 4, EXCP_SWI, syndrome);  // 默认路由到 exception_target_el
    return true;
}
```

`exception_target_el()` 计算默认目标 EL（`op_helper.c:32-45`）：

```c
int exception_target_el(CPUARMState *env)
{
    int target_el = MAX(1, arm_current_el(env));  // 至少 EL1
    // AArch32 Secure 特权模式 → EL3
    if (arm_is_secure(env) && !arm_el_is_aa64(env, 3) && target_el == 1) {
        target_el = 3;
    }
    return target_el;
}
```

### 7.2 HVC（Hypervisor Call：EL1→EL2）

翻译阶段（`translate-a64.c:3173-3191`）：

```c
static bool trans_HVC(DisasContext *s, arg_i *a)
{
    int target_el = s->current_el == 3 ? 3 : 2;  // EL3 执行 HVC 留在 EL3
    if (s->current_el == 0) {
        unallocated_encoding(s);  // EL0 不允许 HVC
        return true;
    }
    gen_a64_update_pc(s, 0);
    gen_helper_pre_hvc(tcg_env);   // 运行时检查是否陷阱
    gen_ss_advance(s);
    gen_exception_insn_el(s, 4, EXCP_HVC, syn_aa64_hvc(a->imm), target_el);
    return true;
}
```

### 7.3 SMC（Secure Monitor Call：→EL3）

翻译阶段（`translate-a64.c:3193-3205`）：

```c
static bool trans_SMC(DisasContext *s, arg_i *a)
{
    if (s->current_el == 0) {
        unallocated_encoding(s);  // EL0 不允许 SMC
        return true;
    }
    gen_a64_update_pc(s, 0);
    gen_helper_pre_smc(tcg_env, ...);  // 运行时检查
    gen_ss_advance(s);
    gen_exception_insn_el(s, 4, EXCP_SMC, syn_aa64_smc(a->imm), 3);  // 始终到 EL3
    return true;
}
```

### 7.4 异常路由总结

```
                    ┌──────────┐
    SVC ──────────→ │   EL1    │ （从 EL0）
                    │ (Kernel) │
    HVC ──────────→ ├──────────┤
                    │   EL2    │ （从 EL1）
                    │(Hyperv.) │
    SMC ──────────→ ├──────────┤
                    │   EL3    │ （从 EL1/EL2）
                    │(Sec.Mon.)│
                    └──────────┘
```

## 8. IRQ/FIQ 中断路由与 EL

### 8.1 路由控制寄存器

中断路由由 HCR_EL2 和 SCR_EL3 共同控制（`cpu-irq.c:15-260`）：

| 控制位 | 作用 |
|--------|------|
| `HCR_EL2.IMO` | 将 EL1 的物理 IRQ 路由到 EL2 |
| `HCR_EL2.FMO` | 将 EL1 的物理 FIQ 路由到 EL2 |
| `HCR_EL2.AMO` | 将 EL1 的 SError 路由到 EL2 |
| `SCR_EL3.IRQ` | 将 IRQ 路由到 EL3 |
| `SCR_EL3.FIQ` | 将 FIQ 路由到 EL3 |

### 8.2 HCR_EL2.TGE 的特殊效果

当 `HCR_EL2.TGE=1` 时，所有 EL0/EL1 异常被重定向到 EL2（`op_helper.c:47-69`）：

```c
void raise_exception(CPUARMState *env, uint32_t excp,
                     uint64_t syndrome, uint32_t target_el)
{
    if (target_el == 1 && (arm_hcr_el2_eff(env) & HCR_TGE)) {
        target_el = 2;  // 重定向 NS EL1 异常到 EL2
        if (syn_get_ec(syndrome) == EC_ADVSIMDFPACCESSTRAP) {
            syndrome = syn_uncategorized();  // FP/SIMD 陷阱 syndrome 调整
        }
    }
    env->exception.target_el = target_el;
    cpu_loop_exit(cs);
}
```

## 9. 系统寄存器访问与 EL 权限检查

### 9.1 访问权限模型

每个系统寄存器通过 `ARMCPRegInfo.access` 字段定义 EL 访问权限。权限检查由 `cp_access_ok()` 实现（`cpregs.h:1122-1126`）：

```c
static inline bool cp_access_ok(int current_el,
                                const ARMCPRegInfo *ri, int isread)
{
    return (ri->access >> ((current_el * 2) + isread)) & 1;
}
```

**权限位编码（每 EL 占 2 位 = 读 + 写）：**

```
access 位布局:
  Bit 0: EL0 读    Bit 1: EL0 写
  Bit 2: EL1 读    Bit 3: EL1 写
  Bit 4: EL2 读    Bit 5: EL2 写
  Bit 6: EL3 读    Bit 7: EL3 写
```

常用权限宏：
- `PL0_RW` = 0xFF（所有 EL 可读写）
- `PL1_RW` = 0xFC（EL1+ 可读写，EL0 不可访问）
- `PL2_RW` = 0xF0（EL2+ 可读写）
- `PL3_RW` = 0xC0（仅 EL3 可读写）

### 9.2 翻译阶段权限检查

在 TCG 翻译时，MRS/MSR 指令通过 `cp_access_ok()` 检查当前 EL 是否有权访问目标寄存器（`translate-a64.c:2823`）：

```c
if (!cp_access_ok(s->current_el, ri, isread)) {
    gen_sysreg_undef(s, isread, op0, op1, op2, crn, crm, rt);
    return;
}
```

如果当前 EL 没有访问权限，生成 UNDEF 异常。

## 10. TB 翻译块与 EL 关联

### 10.1 TB 标志中的 EL 信息

QEMU 不直接将 EL 存储在 TB 标志中，而是通过 `mmu_idx`（MMU 索引）隐式编码当前 EL。翻译时通过 `arm_mmu_idx_to_el()` 反向获取 EL。

`rebuild_hflags_a64()` 构建 TB 标志（`hflags.c:240-430`），其中包含大量 EL 相关信息：

```c
static CPUARMTBFlags rebuild_hflags_a64(CPUARMState *env, int el,
                                         int fp_el, ARMMMUIdx mmu_idx)
{
    CPUARMTBFlags flags = {};
    DP_TBFLAG_ANY(flags, AARCH64_STATE, 1);   // 标记 AArch64 模式
    DP_TBFLAG_A64(flags, TBII, tbii);         // TBI 配置
    DP_TBFLAG_A64(flags, E2H, ...);           // VHE 模式
    DP_TBFLAG_A64(flags, SVEEXC_EL, ...);     // SVE 陷阱 EL
    DP_TBFLAG_A64(flags, PAUTH_ACTIVE, ...);  // 指针认证
    DP_TBFLAG_A64(flags, BT, ...);            // BTI 配置
    DP_TBFLAG_A64(flags, UNPRIV, ...);        // LDTR 非特权访问
    DP_TBFLAG_A64(flags, TRAP_ERET, ...);     // ERET 陷阱
    DP_TBFLAG_A64(flags, NV, ...);            // 嵌套虚拟化
    DP_TBFLAG_A64(flags, MTE_ACTIVE, ...);    // MTE 活跃
    ...
}
```

### 10.2 关键 EL 敏感标志

| 标志 | 含义 | EL 影响 |
|------|------|---------|
| `UNPRIV` | LDTR/STTR 使用非特权访问 | EL1 时设置，受 UAO 影响 |
| `TRAP_ERET` | ERET 需要陷阱 | EL1+NV 或 FGT 时设置 |
| `NV/NV1/NV2` | 嵌套虚拟化 | 仅 EL1 + HCR.NV 时设置 |
| `FGT_ACTIVE` | 细粒度陷阱活跃 | EL0/EL1 时可能设置 |
| `SVEEXC_EL` | SVE 陷阱目标 EL | 取决于当前 EL 和 CPACR/CPTR |
| `E2H` | VHE 模式 | HCR_EL2.E2H |

### 10.3 TB 标志与翻译缓存

当 EL 改变时，hflags 也会改变，这会导致新的 TB 查找/编译。QEMU 通过 `arm_rebuild_hflags()` 在每次 EL 切换后重建 hflags（`hflags.c:521-524`）：

```c
void arm_rebuild_hflags(CPUARMState *env)
{
    env->hflags = rebuild_hflags_internal(env);
}
```

## 11. 特权指令的 EL 相关行为

### 11.1 WFI/WFE 陷阱

WFI/WFE 的陷阱行为是 EL 分层控制的典型示例（`op_helper.c:322-367`）：

```c
static inline int check_wfx_trap(CPUARMState *env, bool is_wfe, uint32_t *excp)
{
    int cur_el = arm_current_el(env);

    // 层级 1：EL0 → EL1 陷阱（SCTLR_EL1.nTWI/nTWE）
    if (cur_el < 1 && arm_feature(env, ARM_FEATURE_V8)) {
        mask = is_wfe ? SCTLR_nTWE : SCTLR_nTWI;
        if (!(arm_sctlr(env, cur_el) & mask)) {
            return exception_target_el(env);
        }
    }

    // 层级 2：EL0/EL1 → EL2 陷阱（HCR_EL2.TWI/TWE）
    if (cur_el < 2) {
        mask = is_wfe ? HCR_TWE : HCR_TWI;
        if (arm_hcr_el2_eff(env) & mask) {
            return 2;
        }
    }

    // 层级 3：→ EL3 陷阱（SCR_EL3.TWI/TWE）
    if (!arm_is_el3_or_mon(env)) {
        mask = is_wfe ? SCR_TWE : SCR_TWI;
        if (env->cp15.scr_el3 & mask) {
            return 3;
        }
    }

    return 0;  // 不陷阱，正常执行
}
```

**陷阱层级示意：**
```
WFI @ EL0
  ├─ SCTLR_EL1.nTWI=0 ? → 陷阱到 EL1
  ├─ HCR_EL2.TWI=1 ?    → 陷阱到 EL2
  └─ SCR_EL3.TWI=1 ?    → 陷阱到 EL3
  └─ 无陷阱              → 正常休眠
```

### 11.2 DAIF 修改

DAIF（Debug/SError/IRQ/FIQ 屏蔽位）的修改受 EL 限制（`helper-a64.c:93-118`）：

```c
static void daif_check(CPUARMState *env, uint32_t op, uint32_t imm, uintptr_t ra)
{
    // EL0 只有在 SCTLR_EL1.UMA=1 时才能修改 DAIF
    if (arm_current_el(env) == 0 && !(arm_sctlr(env, 0) & SCTLR_UMA)) {
        raise_exception_ra(env, EXCP_UDEF, ..., exception_target_el(env), ra);
    }
}
```

### 11.3 AT（地址翻译）指令

AT 指令的行为完全依赖 EL（`cpregs-at.c:291-447`）：
- `AT S1E0R/W`：以 EL0 权限翻译（从 EL1 执行）
- `AT S1E1R/W`：以 EL1 权限翻译
- `AT S1E2R/W`：以 EL2 权限翻译
- `AT S1E3R/W`：以 EL3 权限翻译
- `AT S12E0/1R/W`：两阶段翻译（Stage1 + Stage2）

### 11.4 TLBI 指令

TLBI 的作用范围受 EL 影响（`tlb-insns.c:17-90`）：
- EL1 执行 TLBI 可被 HCR_EL2.TTLB/TTLBIS 陷阱到 EL2
- EL2 执行的 TLBI 影响整个 Inner Shareable domain
- EL3 执行的 TLBI 可以作用于所有安全状态

## 12. 陷阱配置与细粒度陷阱

### 12.1 粗粒度陷阱

| 控制寄存器 | 控制位 | 作用 |
|-----------|--------|------|
| `CPACR_EL1` | FPEN | EL0/EL1 FP/SIMD 访问陷阱到 EL1 |
| `CPTR_EL2` | TFP | FP/SIMD 访问陷阱到 EL2 |
| `CPTR_EL3` | TFP | FP/SIMD 访问陷阱到 EL3 |
| `HCR_EL2` | TGE | EL0/EL1 所有异常路由到 EL2 |
| `HCR_EL2` | TIDCP | 实现定义 CP 访问陷阱到 EL2 |
| `SCR_EL3` | SMD | 禁止 SMC（陷阱为 UNDEF） |

### 12.2 细粒度陷阱（FEAT_FGT）

QEMU 支持 FEAT_FGT，通过 `arm_fgt_active()` 检查 FGT 是否活跃（`hflags.c:374-382`）：

```c
if (arm_fgt_active(env, el)) {
    DP_TBFLAG_ANY(flags, FGT_ACTIVE, 1);
    if (FIELD_EX64(env->cp15.fgt_exec[FGTREG_HFGITR], HFGITR_EL2, ERET)) {
        DP_TBFLAG_A64(flags, TRAP_ERET, 1);  // ERET 指令陷阱
    }
    if (fgt_svc(env, el)) {
        DP_TBFLAG_ANY(flags, FGT_SVC, 1);    // SVC 指令陷阱
    }
}
```

FGT 允许 EL2 对 EL1 的单个系统寄存器访问进行精确陷阱控制，而不是粗粒度地陷阱所有访问。

## 13. MMU 模式与 EL 映射

### 13.1 ARMMMUIdx 枚举

QEMU 定义了丰富的 MMU 索引来映射不同 EL 的地址翻译配置（`mmuidx.h:137-185`）：

```
ARMMMUIdx_E10_0      → EL0，使用 EL1&0 翻译方案（TTBR0_EL1/TTBR1_EL1）
ARMMMUIdx_E10_1      → EL1，使用 EL1&0 翻译方案
ARMMMUIdx_E10_1_PAN  → EL1 + PAN 使能
ARMMMUIdx_E20_0      → EL0，VHE 模式（TTBR0_EL2/TTBR1_EL2）
ARMMMUIdx_E20_2      → EL2，VHE 模式
ARMMMUIdx_E20_2_PAN  → EL2 + PAN（VHE）
ARMMMUIdx_E2         → EL2，非 VHE（TTBR0_EL2 仅）
ARMMMUIdx_E3         → EL3（TTBR0_EL3 仅）
ARMMMUIdx_E30_0      → AArch32 Secure EL0
ARMMMUIdx_E30_3_PAN  → AArch32 Secure EL3 + PAN
```

### 13.2 EL 到 MMU 索引映射

`arm_mmu_idx_el()` 实现映射逻辑（`helper.c:9957-10008`）：

```c
ARMMMUIdx arm_mmu_idx_el(CPUARMState *env, int el)
{
    switch (el) {
    case 0:
        if ((hcr & (HCR_E2H | HCR_TGE)) == (HCR_E2H | HCR_TGE)) {
            return ARMMMUIdx_E20_0;      // VHE + TGE → EL2 翻译方案
        }
        if (arm_is_secure_below_el3(env) && !arm_el_is_aa64(env, 3)) {
            return ARMMMUIdx_E30_0;      // AArch32 Secure
        }
        return ARMMMUIdx_E10_0;          // 标准 EL0
    case 1:
        return arm_pan_enabled(env) ? ARMMMUIdx_E10_1_PAN : ARMMMUIdx_E10_1;
    case 2:
        if (hcr & HCR_E2H) {
            return arm_pan_enabled(env) ? ARMMMUIdx_E20_2_PAN : ARMMMUIdx_E20_2;
        }
        return ARMMMUIdx_E2;
    case 3:
        if (!arm_el_is_aa64(env, 3) && arm_pan_enabled(env))
            return ARMMMUIdx_E30_3_PAN;
        return ARMMMUIdx_E3;
    }
}
```

### 13.3 regime_el()——从 MMU 索引反向查 EL

`regime_el()` 通过查表获取翻译方案的控制 EL（`mmuidx-internal.h:42-47`）：

```c
static inline uint32_t regime_el(ARMMMUIdx idx)
{
    return FIELD_EX32(arm_mmuidx_table[idx], MMUIDXINFO, REL);
}
```

此函数在页表遍历（PTW）中大量使用，决定使用哪个 TTBR/TCR/SCTLR。

## 14. PAN/UAO 与内存访问控制

### 14.1 PAN（Privileged Access Never）

PAN 使得 EL1（或 VHE 的 EL2）无法直接访问 EL0 可访问的内存，防止内核意外读写用户空间：

- 在 MMU 索引中体现为 `_PAN` 后缀（如 `ARMMMUIdx_E10_1_PAN`）
- 异常进入时，如果 `SCTLR.SPAN=0`，PAN 会被自动设置为 1（`helper.c:9386-9392`）：
  ```c
  if ((env->cp15.sctlr_el[new_el] & SCTLR_SPAN) == 0) {
      new_mode |= PSTATE_PAN;  // 进入 EL1 时自动启用 PAN
  }
  ```

### 14.2 UAO（User Access Override）

UAO 改变 LDTR/STTR（非特权加载/存储）的行为。当 `PSTATE.UAO=1` 时，LDTR/STTR 的行为与普通 LDR/STR 相同（`hflags.c:345-368`）：

```c
// 当 UAO=0 时才设置 UNPRIV 标志
if (!(env->pstate & PSTATE_UAO)) {
    switch (mmu_idx) {
    case ARMMMUIdx_E10_1:
    case ARMMMUIdx_E10_1_PAN:
        DP_TBFLAG_A64(flags, UNPRIV, 1);  // EL1 的 LDTR 使用 EL0 权限
        break;
    case ARMMMUIdx_E20_2:
    case ARMMMUIdx_E20_2_PAN:
        if (env->cp15.hcr_el2 & HCR_TGE) {
            DP_TBFLAG_A64(flags, UNPRIV, 1);  // VHE EL2 的 LDTR
        }
        break;
    }
}
```

## 15. EL 切换的副作用

### 15.1 hflags 重建

每次 EL 切换后必须重建 hflags：
- 异常进入：`helper.c:9419-9421`
- 异常返回：`helper-a64.c:714,728,782`

### 15.2 TLB 处理

QEMU **不在 EL 切换时显式刷新 TLB**。原因是 QEMU 的 TLB 以 `mmu_idx` 为索引，不同 EL 使用不同的 `mmu_idx`，因此天然隔离。TLB 刷新仅在以下情况发生：
- 显式 TLBI 指令
- 修改 TCR/TTBR/SCTLR 等 MMU 配置寄存器

### 15.3 独占监控器清除

ERET 时清除独占监控器（`helper-a64.c:633`）：
```c
arm_clear_exclusive(env);
```
这确保 LDREX/STREX 的独占状态不会跨异常边界泄露。

### 15.4 EL 切换钩子

QEMU 提供 EL 切换前后的钩子机制（`helper-a64.c:693-695,760-762`）：
```c
arm_call_pre_el_change_hook(cpu);   // 切换前
// ... 执行 EL 切换 ...
arm_call_el_change_hook(cpu);       // 切换后
```

## 16. SVE/SME 状态与 EL 切换

### 16.1 向量长度调整

`aarch64_sve_change_el()` 在 EL 切换时处理 SVE/SME 状态（`helper.c:10073-10128`）：

```c
void aarch64_sve_change_el(CPUARMState *env, int old_el,
                            int new_el, bool el0_a64)
{
    // 如果 FP 在任一 EL 被禁用，无需处理
    if (fp_exception_el(env, old_el) || fp_exception_el(env, new_el)) return;

    old_a64 = old_el ? arm_el_is_aa64(env, old_el) : el0_a64;
    new_a64 = new_el ? arm_el_is_aa64(env, new_el) : el0_a64;

    // AArch64↔AArch32 切换 + SM 模式 → 重置 SVE 状态
    sm = FIELD_EX64(env->svcr, SVCR, SM);
    if (old_a64 != new_a64 && sm) {
        arm_reset_sve_state(env);
        return;
    }

    // 计算两个 EL 的有效向量长度
    old_len = old_a64 ? sve_vqm1_for_el_sm_ena(env, old_el, sm) : 0;
    new_len = new_a64 ? sve_vqm1_for_el_sm_ena(env, new_el, sm) : 0;

    // 如果新 EL 的 VL 更短，截断寄存器
    if (new_len < old_len) {
        aarch64_sve_narrow_vq(env, new_len + 1);
    }
}
```

**关键点：** 不同 EL 可通过 ZCR_ELx.LEN 配置不同的最大向量长度。当从高向量长度 EL 切换到低向量长度 EL 时，高位寄存器内容被清零。

### 16.2 调用时机

- 异常进入（`helper.c:9214`）：
  ```c
  aarch64_sve_change_el(env, cur_el, new_el, is_a64(env));
  ```
- 异常返回（`helper-a64.c:758`）：
  ```c
  aarch64_sve_change_el(env, cur_el, new_el, return_to_aa64);
  ```

## 17. KVM 模式下的 EL 管理

### 17.1 硬件 vs 软件 EL 切换

在 KVM 模式下，大部分 EL 切换由硬件直接处理：
- Guest OS 的 EL0↔EL1 切换完全在硬件中完成
- Guest OS 的中断/异常处理在硬件中完成
- QEMU 仅在 VM Exit 时同步状态

### 17.2 状态同步

KVM vCPU 状态同步时涉及 EL 相关字段（`kvm.c:1958-2055,2342-2405`）：

- 从 KVM 读取 PSTATE/PC/SP/ELR_EL1
- 使用 `aarch64_restore_sp(env, 1)` 恢复 SP banking

### 17.3 陷阱处理

KVM 处理的关键陷阱类型（`kvm.c:1546-1567`）：
- `KVM_EXIT_ARM_NISV`：不支持的指令模拟
- `KVM_EXIT_SYSTEM_EVENT`：关机/重启/Guest Panic

对于 HVC/SMC，KVM 可以配置是否陷阱到用户空间（QEMU），由 `KVM_EXIT_SYSTEM_EVENT` 处理（`kvm-all.c:3577-3600`）。

## 18. 非法异常返回处理

当 ERET 检测到非法返回条件时，执行特殊的恢复逻辑（`helper-a64.c:766-785`）：

```c
illegal_return:
    // 1. 设置 PSTATE.IL（Illegal Execution State）
    env->pstate |= PSTATE_IL;
    // 2. PC 仍然从 ELR 恢复
    env->pc = new_pc;
    // 3. 仅恢复 NZCV + DAIF + ALLINT，其余保持不变
    spsr &= PSTATE_NZCV | PSTATE_DAIF | PSTATE_ALLINT;
    spsr |= pstate_read(env) & ~(PSTATE_NZCV | PSTATE_DAIF | PSTATE_ALLINT);
    pstate_write(env, spsr);
    // 4. 不改变 EL、执行状态、栈指针
    helper_rebuild_hflags_a64(env, cur_el);
```

**非法返回的后果：**
- CPU 继续在当前 EL 执行
- 设置 `PSTATE.IL=1`，后续任何指令执行都会产生 Illegal Execution State 异常
- 这是一种安全保护机制，防止通过构造恶意 SPSR 进行 EL 提权

```
    │
    └─ 继续执行 @ EL0       查找/编译新 TB（hflags 已变）
```

### 20.2 EL 切换核心要点

1. **EL 编码在 PSTATE[3:2]**，通过 `arm_current_el()` 读取
2. **每个 EL 拥有独立的 SP/ELR/SPSR**，通过 banking 数组管理
3. **异常进入保存 PSTATE→SPSR、PC→ELR**，设置新 PSTATE（DAIF 全屏蔽 + 目标 EL 模式）
4. **异常返回通过 ERET**，从 SPSR 恢复 PSTATE，从 ELR 恢复 PC
5. **TB 通过 mmu_idx 隐式关联 EL**，EL 变化导致 hflags 重建和 TB 重新查找
6. **系统寄存器访问受 EL 权限矩阵控制**，由 `cp_access_ok()` 在翻译时检查
7. **MMU 配置按 EL 隔离**，通过 `ARMMMUIdx` 枚举区分不同翻译方案
8. **SVE/SME 向量长度按 EL 独立配置**，EL 切换时可能截断寄存器
9. **非法 ERET 设置 PSTATE.IL**，保持当前 EL 不变
10. **KVM 模式下 EL 切换由硬件完成**，QEMU 仅在 VM Exit 时同步状态
